Production Case Study: How Continental Road Routing Works in 1 Millisecond (Contraction Hierarchies & Hub Labeling)

5 min read Module 5.2: Disjoint Sets, Minimum Spanning Trees & Shortest Paths Updated Oct 23, 2026
📄 Cheat Sheet
Nathan Sturtevant Contraction Hierarchies: Vertex Importance Ordering, Shortcuts & Bidirectional Road Routing Watch on YouTube ↗

Explains why standard Dijkstra and A* are too slow for continental road networks and how hierarchical preprocessing enables sub-millisecond queries.

Intuition first

A continental road network (such as Europe or North America in OpenStreetMap) contains $|V| \approx 5 \times 10^7$ intersections and $|E| \approx 1.2 \times 10^8$ road segments. Running standard Dijkstra from Lisbon to Moscow visits 50 million vertices and takes 3 to 8 seconds—even with A* Euclidean heuristics, it still takes hundreds of milliseconds, which is $500\times$ too slow for ride-sharing dispatch or logistics engines handling $10{,}000$ queries per second.

Production routing engines like OSRM (Open Source Routing Machine) and Valhalla achieve 0.3-millisecond queries via Contraction Hierarchies (CH, Geisberger et al. 2008): an offline preprocessing phase orders vertices by highway importance and inserts shortcut edges so that an online bidirectional search only climbs upward in rank, visiting fewer than 400 vertices per continental query!

The Mechanics of Contraction Hierarchies (CH)

Contraction Hierarchies separate routing into two phases: a one-time offline preprocessing phase (taking ~10 minutes for a continent) and an ultra-fast online query phase.

Formal Invariant — Witness Search & Upward-Downward Path Canonical Form

Assign every vertex $v \in V$ a distinct importance rank $\text{rank}(v) \in \{1, 2, \dots, |V|\}$ (residential dead-ends lowest, interstate highway junctions highest). We contract vertices one by one in increasing order of rank:

When contracting vertex $v$, for every pair of remaining higher-rank neighbors $(u, w)$ with $\text{rank}(u) > \text{rank}(v)$ and $\text{rank}(w) > \text{rank}(v)$ such that edges $(u, v)$ and $(v, w)$ exist, we run a local witness search to check if the shortest path $\delta(u, w)$ in the remaining graph is strictly $\le w(u, v) + w(v, w)$ without using $v$. If not (i.e., $u \to v \to w$ is the unique shortest path), we insert a shortcut edge $(u, w)$ of weight $w(u, v) + w(v, w)$.

CH Optimality Theorem: In the shortcut-augmented graph $G^*$, for every pair $(s, t) \in V \times V$, there exists a shortest path of the canonical up-down form:

$$s = u_0 \to u_1 \to \dots \to u_p = m = v_q \to \dots \to v_0 = t$$

where ranks strictly increase along the forward prefix ($ ext{rank}(u_0) < dots < ext{rank}(u_p)$) and strictly decrease along the suffix ($ ext{rank}(v_q) > dots > ext{rank}(v_0)$) meeting at the maximum-rank apex vertex $m$!

1. Online Query: Upward-Only Bidirectional Dijkstra

Because every shortest path has an up-down canonical representation in $G^*$, the online query runs two miniature Dijkstras simultaneously:

  • Forward Search from $s$ in $G^\uparrow$: Only traverses outgoing edges $(u, x)$ where $\text{rank}(x) > \text{rank}(u)$.
  • Backward Search from $t$ in $G^\downarrow$: Only traverses incoming edges $(y, v)$ where $\text{rank}(y) > \text{rank}(v)$.

Because both searches strictly climb the hierarchy toward major highway arterials, the search trees contain only $\approx 200$ vertices each! The true shortest path distance is $\min_{m \in V} (d^\uparrow[m] + d^\downarrow[m])$ over all meeting vertices $m$.

2. Edge-Difference Heuristic & Hub Labeling (2-Hop Cover)

How do we choose the contraction order? Contracting a vertex $v$ deletes $\text{deg}(v)$ incident edges and adds $s(v)$ shortcuts. Ordering vertices by a priority queue of Edge Difference $\Delta(v) = s(v) - \text{deg}(v)$ (plus contracted neighbor depth) keeps the total number of added shortcuts below $0.4 |E|$. Taking this one step further, Hub Labeling (Abraham et al. 2011) stores each vertex's tiny upward search space $L_f(s)$ and $L_b(t)$ as sorted arrays of (hubId, dist), reducing shortest-path queries to a $0.5$-microsecond sorted-array merge intersection!

Hardware Reality — Stall-on-Demand & Unpacking Shortcuts

To reconstruct the full turn-by-turn geometry of a route without storing path lists on every shortcut, each shortcut edge $e = (u, w)$ stores only a single 32-bit integer: middleVertex = v. Once the optimal meeting apex $m$ is found, a recursive in-order traversal unpacks $(u, w) \to (u, v) + (v, w)$ in $O(|P|)$ time proportional to the number of edges on the final path!

Production Implementation: CH Upward-Only Bidirectional Query & Shortcut Unpacker

C++20
#include <vector>
#include <queue>
#include <limits>
#include <algorithm>

struct CHShortcutEdge {
    int to;
    long long weight;
    int middleVertex; // -1 if original road edge, else contracted vertex v
};

class ContractionHierarchyRouter {
public:
    ContractionHierarchyRouter(int n, std::vector<int> rankOrder,
                               std::vector<std::vector<CHShortcutEdge>> upFwd,
                               std::vector<std::vector<CHShortcutEdge>> upBwd)
        : numVertices(n), rank(std::move(rankOrder)),
          adjUp(std::move(upFwd)), revUp(std::move(upBwd)) {}

    long long queryDistance(int s, int t) const {
        constexpr long long INF = std::numeric_limits<long long>::max() / 4;
        std::vector<long long> dF(numVertices, INF), dB(numVertices, INF);
        using State = std::pair<long long, int>;
        std::priority_queue<State, std::vector<State>, std::greater<State>> pqF, pqB;

        dF[s] = 0; pqF.emplace(0, s);
        dB[t] = 0; pqB.emplace(0, t);
        long long best = INF;

        while (!pqF.empty() || !pqB.empty()) {
            if (!pqF.empty()) {
                auto [d, u] = pqF.top(); pqF.pop();
                if (d <= dF[u] && d < best) {
                    best = std::min(best, d + dB[u]);
                    for (const auto& e : adjUp[u]) {
                        if (rank[e.to] > rank[u] && d + e.weight < dF[e.to]) {
                            dF[e.to] = d + e.weight;
                            pqF.emplace(dF[e.to], e.to);
                        }
                    }
                }
            }
            if (!pqB.empty()) {
                auto [d, u] = pqB.top(); pqB.pop();
                if (d <= dB[u] && d < best) {
                    best = std::min(best, dF[u] + d);
                    for (const auto& e : revUp[u]) {
                        if (rank[e.to] > rank[u] && d + e.weight < dB[e.to]) {
                            dB[e.to] = d + e.weight;
                            pqB.emplace(dB[e.to], e.to);
                        }
                    }
                }
            }
        }
        return best == INF ? -1 : best;
    }

private:
    int numVertices;
    std::vector<int> rank;
    std::vector<std::vector<CHShortcutEdge>> adjUp, revUp;
};
Failure Mode — Stopping Bidirectional CH on the First Meeting Vertex

In both standard Bidirectional Dijkstra and Contraction Hierarchies, the first vertex $v$ reached by both the forward and backward searches is not necessarily the optimal apex $m$! You must maintain an upper bound best = min(best, dF[u] + dB[u]) and continue expanding each queue until its minimum key exceeds best.

Concept Check When Contraction Hierarchies Add a Shortcut Edge recall
Section: Witness Search & Shortcuts

During the preprocessing phase of Contraction Hierarchies (CH), when node $v$ is contracted between neighbor $u$ (with incoming edge $(u, v)$) and neighbor $w$ (with outgoing edge $(v, w)$), when must a shortcut edge $(u, w)$ of weight $w(u, v) + w(v, w)$ be added?

A local witness Dijkstra checks if an alternative path u ~> w of weight <= w(u,v) + w(v,w) exists avoiding v. Only if no such witness exists is the shortcut (u, w) necessary to preserve all shortest-path distances.
Concept Check Why Bidirectional CH Queries Only Relax Upward Edges apply
Section: Upward-Only Query Invariant

At query time in a Contraction Hierarchy with node importance ranks $r(u)$, the forward search from $s$ only relaxes edges $(u, v)$ with $r(u) < r(v)$, and the backward search from $t$ only relaxes reversed edges $(w, v)$ with $r(w) < r(v)$. Why does this always find the exact shortest path?

Any interior local minimum in rank along a shortest path (`r(a) > r(b) < r(c)`) was eliminated when `b` was contracted before `a` and `c` and replaced by the shortcut `(a, c)`. Thus a Valley-free / unimodal path peaking at apex `u_p` always exists.
Concept Check Choosing Contraction Order via Edge Difference apply
Section: Edge Difference Heuristic

Why do Contraction Hierarchy preprocessors order vertices for contraction by increasing **Edge Difference** ($\text{shortcuts added} - \text{incident edges removed}$)?

Contracting a major hub of degree d first could insert up to d(d-1) shortcuts, exploding graph density. Contracting low-edge-difference nodes first strips local streets cleanly before touching arterial highways.
Concept Check Customizable Contraction Hierarchies (CCH) vs Standard CH staff
Section: Dynamic Traffic Updates

In a live navigation system like Google Maps or OSRM where live traffic updates edge travel times every 30 seconds, why is a 3-phase **Customizable Contraction Hierarchy (CCH)** used instead of re-running full CH preprocessing from scratch?

Decoupling metric-independent topological contraction (nested dissection separator ordering) from metric-dependent triangle weight relaxation lets production routing engines ingest live traffic updates in sub-second cycles.

Decoupling metric-independent topological contraction (nested dissection separator ordering) from metric-dependent triangle weight relaxation lets production routing engines ingest live traffic updates in sub-second cycles.

Key Takeaways

Contraction Hierarchies (CH) contract vertices in increasing order of importance, adding a shortcut (u, w) whenever u -> v -> w is the unique shortest path between higher-rank neighbors.
Every shortest path in the shortcut-augmented graph has a canonical up-down form that climbs in rank from s to an apex m and descends in rank from m to t.
Online CH queries run bidirectional Dijkstra restricted strictly to upward edges (rank[next] > rank[cur]), visiting ~350 nodes instead of 50 million.
Storing a single middleVertex integer per shortcut enables recursive unpacking into the full original road geometry in O(|path|) time.
