Deep-dive lecture covering Production Case Study: Redis ZSET (Listpack vs SkipList + Dict Dual Indexing).

Intuition first

How does a Redis Sorted Set (ZSET) support ZSCORE member (point lookup by string key) in $O(1)$ time, ZRANGEBYSCORE min max (1D range query by floating-point score) in $O(\log N + M)$ time, AND ZRANK member / ZRANGE start stop (positional rank queries) in $O(\log N + M)$ time? By adaptively switching from a flat cache-local listpack for small sets ($\le 128$ items) to a dual-indexed dict + rank-augmented zskiplist for large sets.

0:00 / 2:59

Dual-Indexing Architecture: Why Redis Combines a Hash Table + Augmented Skip List

Consider the API contract of a Redis Sorted Set (ZSET, implemented in src/t_zset.c by Salvatore Sanfilippo): every element is a unique string ele paired with a 64-bit IEEE-754 floating-point double score, ordered primarily by score ascending and secondarily by lexicographical ele ascending. Look at the conflicting access patterns required:

  • ZSCORE key member asks: "What is the score of member $X$?" A pure Skip List or B-Tree ordered by (score, ele) cannot search by ele alone without scanning all $N$ nodes in $O(N)$ time!
  • ZRANGEBYSCORE key min max asks: "Return all members with score $\in [\text{min}, \text{max}]$." A hash table keyed by ele cannot answer ordered range queries without an $O(N \log N)$ sort!
  • ZRANK key member and ZRANGE key 100 150 ask: "What is the 0-based positional index of member $X$?" and "Return the 100th through 150th elements."

Redis solves all three simultaneously inside struct zset by composing two structures that share the exact same underlying string allocations (sds):

  1. A Hash Table (dict *dict): Maps ele -> score in $O(1)$ time.
  2. An Order-Statistic Skip List (zskiplist *zsl): Indexes (score, ele) in sorted order, augmented with level span counters and a level-0 backward pointer.
Structural Invariant: Skip List span Augmentation for $O(\log N)$ Rank Queries

Inside Redis's zskiplistNode, each level $k$ in the tower stores not just a forward pointer zskiplistNode *forward, but also an unsigned integer unsigned long span:

$$\text{level}[k].\text{span} = \text{number of level-0 nodes traversed from } u \text{ to } u.\text{level}[k].\text{forward}$$

How does ZRANK key member compute the exact 0-based rank of member in $O(\log N)$ time?

  1. First, look up score = dictFind(zset->dict, member) in $O(1)$ time!
  2. Second, search the Skip List for the composite key (score, member) from top level down to level 0. Every time we step horizontally across curr->level[k].forward, we add rank += curr->level[k].span! When we reach the target node at level 0, the accumulated rank is its exact 1-based position in the sorted set!

Hardware Reality: Why Redis Eliminated ziplist Cascade Updates with listpack

To support reverse iteration (ZREVRANGE), Redis's original compact format (ziplist) stored a variable-length field prevrawlen at the start of each entry: 1 byte if the previous entry was $< 254$ bytes, or 5 bytes if $\ge 254$ bytes. Imagine a ziplist where thousands of consecutive entries are each 253 bytes long. Inserting a single 300-byte entry before them forced the next entry's prevrawlen to expand from 1 byte to 5 bytes—growing that entry from 253 bytes to 257 bytes ($ge 254$), which forced the next entry to expand to 5 bytes, triggering a catastrophic $O(N^2)$ cascading reallocation storm! Salvatore Sanfilippo solved this in listpack: each entry stores its own length at the end of the entry ([encoding | data | backlen]), so forward scans read left-to-right and backward scans read backlen right-to-left, making every entry's byte size 100% independent of its neighbors!

Production Implementation: Order-Statistic Skip List Node with rank & get_by_rank

C++20
#include <array>
#include <cstddef>
#include <cstdint>
#include <string>

// Simplified Redis-style Order-Statistic Skip List supporting O(log N) Rank & Select
class RankedSkipList {
  static constexpr int MAX_LEVEL = 16;

  struct LevelLink {
    int next_idx = 0;       // 0 = nullptr sentinel
    std::size_t span = 0;   // Number of level-0 nodes skipped by this link
  };

  struct Node {
    double score = 0.0;
    int member_id = 0;
    int backward = 0;
    std::array<LevelLink, MAX_LEVEL> level{};
  };

  std::array<Node, 4096> pool_{}; // Contiguous pool; index 0 is head sentinel
  int pool_used_ = 1;
  int max_lvl_ = 1;

  static bool less_than(double s1, int m1, double s2, int m2) noexcept {
    return (s1 < s2) || (s1 == s2 && m1 < m2);
  }

public:
  // O(log N) ZRANK: Returns 1-based rank of (score, member_id), or 0 if not found
  std::size_t get_rank(double score, int member_id) const noexcept {
    std::size_t rank = 0;
    int x = 0; // Start at head (index 0)
    for (int i = max_lvl_ - 1; i >= 0; --i) {
      while (pool_[x].level[i].next_idx != 0) {
        const int nxt = pool_[x].level[i].next_idx;
        if (less_than(pool_[nxt].score, pool_[nxt].member_id, score, member_id) ||
            (pool_[nxt].score == score && pool_[nxt].member_id == member_id)) {
          rank += pool_[x].level[i].span;
          x = nxt;
        } else {
          break;
        }
      }
      if (x != 0 && pool_[x].score == score && pool_[x].member_id == member_id) {
        return rank;
      }
    }
    return 0;
  }

  // O(log N) ZRANGE by Rank: Retrieve node at 1-based positional rank target_rank
  const Node* get_element_by_rank(std::size_t target_rank) const noexcept {
    std::size_t traversed = 0;
    int x = 0;
    for (int i = max_lvl_ - 1; i >= 0; --i) {
      while (pool_[x].level[i].next_idx != 0 &&
             traversed + pool_[x].level[i].span <= target_rank) {
        traversed += pool_[x].level[i].span;
        x = pool_[x].level[i].next_idx;
      }
      if (traversed == target_rank) return &pool_[x];
    }
    return nullptr;
  }
};
Production Pitfall: Updating a Member's Score in a Skip List Without Deleting and Reinserting

When a user executes ZADD key new_score existing_member in Redis, can you simply look up the node via the hash table and overwrite node->score = new_score in place? Only if the node's relative sorted position between its level-0 predecessor and successor does not change! If new_score moves the node past even a single neighbor, overwriting score in place corrupts the sorted invariant of every Skip List level and breaks all span counters. Redis explicitly checks whether the new score still lies strictly between node->backward->score and node->level[0].forward->score; if not, it deletes the node (decrementing span on untouched upper levels) and reinserts it at its new position.

Check yourself Question 1 of 4
Concept Check Dual-Indexed `OBJ_ENCODING_SKIPLIST` Architecture recall

When a Redis Sorted Set (`ZSET`) exceeds `zset-max-listpack-entries` (default 128), Redis converts it to `OBJ_ENCODING_SKIPLIST`, which contains both a `dict` (hash table) and a `zskiplist`. Why are BOTH data structures required inside the same `zset` struct?

A skip list sorted by `(score, member)` cannot locate a member in $O(\log N)$ time unless its current `score` is already known! The `dict` resolves `member -> score` in $O(1)$ time (sharing the underlying `sds` string pointer with the skip list to avoid duplicating strings), and then the skip list uses `(score, member)` to find, update, or rank the node in $O(\log N)$.
Concept Check Skip List `span` Field and $O(\log N)$ `ZRANK` apply

In Redis's `zskiplistLevel` struct, every forward pointer `level[i].forward` is paired with an `unsigned long span`. How does Redis compute the 0-based rank of a target `(score, member)` in $O(\log N)$ time during `ZRANK`?

Augmenting each forward pointer at level $i$ with the count of level-0 nodes it skips (`span`) turns the skip list into an order-statistic structure. Whenever the search moves right along `level[i]`, it adds `level[i].span` to a running `rank` counter, reaching the target node in $O(\log N)$ pointer hops with its exact rank.
Concept Check The `ziplist` Cascade Update Bug vs `listpack` Fix apply

In legacy Redis (`ziplist`), every entry started with `[prevlen][encoding][data]`, where `prevlen` used 1 byte if the previous entry was $\le 253$ bytes, or 5 bytes if the previous entry was $\ge 254$ bytes. How did this design allow a single insertion to trigger an $O(N^2)$ cascade update, and how did Salvatore Sanfilippo's `listpack` eliminate it?

Because `ziplist` stored the *previous* entry's length inside the *next* entry, changing entry $k$'s size could alter entry $k+1$'s size, triggering a domino effect of `memmove` expansions. In `listpack`, each entry ends with `backlen` (the length of *itself*, read right-to-left using MSB continuation bits), so backward traversal still works (jump back by the previous entry's trailing `backlen`), and no entry ever depends on its neighbor's size.
Concept Check Why Redis Uses $p = 1/4$ and `ZSKIPLIST_MAXLEVEL = 32` staff

In `src/server.h`, Redis defines `#define ZSKIPLIST_MAXLEVEL 32` (64 in older versions) and `#define ZSKIPLIST_P 0.25`. Compared to a textbook skip list with $p = 0.5$, what is the exact quantitative trade-off of setting $p = 0.25$?

In Redis, each `zskiplistLevel` is 16 bytes (8B `forward` pointer + 8B `span`). Lowering $p$ from $1/2$ to $1/4$ shrinks the expected tower height from $2.0$ to $1.333$, saving ~11 bytes per node across millions of sorted set elements. With `MAXLEVEL = 32` and $p = 1/4$, the top level reaches $4^{32} = 2^{64}$ elements, and the flatter fanout of 4 behaves very similarly to a 4-way B-tree.

Key Takeaways

Redis ZSETs combine a hash table (dict: member -> score) for O(1) point lookups with an order-statistic Skip List (zskiplist: (score, member)) for O(log N) range and rank queries.
Augmenting each Skip List forward pointer with a span counter (number of level-0 nodes skipped) enables O(log N) positional rank lookup (ZRANK) and k-th element selection (ZRANGE).
For small ZSETs (<= 128 elements, <= 64B strings), Redis uses a single contiguous listpack array instead of a Skip List + Dict, saving 10x memory and exploiting L1 cache locality.
Redis 7.0 replaced ziplist with listpack by moving each entry's length field (backlen) to the end of the entry itself, eliminating O(N^2) cascading length-expansion updates.
