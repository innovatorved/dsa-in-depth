Robust Computational Geometry Primitives: 2D Cross/Dot Products, CCW Orientation & Segment Intersection

Errichto Algorithms Computational Geometry Primitives: Cross Products, Orientation & Segment Intersection Watch on YouTube ↗

Demonstrates why slope-based geometry fails on vertical lines and floating-point rounding, and how exact 64-bit integer cross/dot products solve orientation, segment intersection, and polygon area without division.

Intuition first

In naive geometry code, computing slopes Δy/Δx\Delta y / \Delta xΔy/Δx triggers division-by-zero on vertical segments and catastrophic floating-point cancellation on nearly parallel lines. Every foundational 2D geometric predicate—whether three points turn counter-clockwise (CCW), whether two line segments intersect, whether a point lies inside a polygon, or the area of a non-self-intersecting polygon—reduces to two division-free bilinear forms over exact 64-bit integers: the 2D Cross Product u⃗×v⃗=uxvy−uyvx\vec{u} \times \vec{v} = u_x v_y - u_y v_xu×v=ux​vy​−uy​vx​ (signed parallelogram area) and the Dot Product u⃗⋅v⃗=uxvx+uyvy\vec{u} \cdot \vec{v} = u_x v_x + u_y v_yu⋅v=ux​vx​+uy​vy​ (signed projection).

3. Why sgn() Normalization Prevents Overflow

If coordinates satisfy ∣x∣,∣y∣≤109|x|, |y| \le 10^9∣x∣,∣y∣≤109, then cross(A,B,C)\text{cross}(A, B, C)cross(A,B,C) is bounded by 4×10184 \times 10^{18}4×1018, which fits inside a signed 64-bit integer (int64_t max ≈9.22×1018\approx 9.22 \times 10^{18}≈9.22×1018). However, if you test opposite orientations by multiplying cross(A,B,C)×cross(A,B,D)<0\text{cross}(A, B, C) \times \text{cross}(A, B, D) < 0cross(A,B,C)×cross(A,B,D)<0 directly in int64_t, the product reaches 1.6×10371.6 \times 10^{37}1.6×1037 and overflows! Mapping each cross product through sgn(v)∈{−1,0,+1}\text{sgn}(v) \in \{-1, 0, +1\}sgn(v)∈{−1,0,+1} first reduces the product to {−1,0,+1}\{-1, 0, +1\}{−1,0,+1} with zero overflow risk.

4. Hardware & Floating-Point Realities

IEEE-754 Catastrophic Cancellation vs Exact Integer Predicates

In IEEE-754 double (53-bit significand), subtracting two nearly equal products uxvy−uyvxu_x v_y - u_y v_xux​vy​−uy​vx​ loses all leading matching bits (catastrophic cancellation), which can flip the sign of cross(A, B, C) from positive to negative and cause Convex Hull or Delaunay Triangulation algorithms to enter infinite loops! Production CAD/GIS kernels (CGAL, Jonathan Shewchuk's Adaptive Precision Floating-Point Predicates) use a fast hardware floating-point filter first and fall back to exact multi-word expansion arithmetic only when ∣uxvy−uyvx∣|u_x v_y - u_y v_x|∣ux​vy​−uy​vx​∣ is smaller than the rounding error bound.

6. Production-Grade C++20 Implementation

C++2060 lines
#include <cstdint>
#include <vector>
#include <cmath>

struct Point {
    int64_t x = 0, y = 0;
    Point operator-(const Point& o) const { return {x - o.x, y - o.y}; }
    Point operator+(const Point& o) const { return {x + o.x, y + o.y}; }
};

inline int64_t dot(const Point& u, const Point& v) {
    return u.x * v.x + u.y * v.y;
}

inline int64_t cross(const Point& u, const Point& v) {
    return u.x * v.y - u.y * v.x;
}

// Twice the signed area of triangle ABC (>0: CCW, <0: CW, 0: collinear)
inline int64_t cross(const Point& a, const Point& b, const Point& c) {
    return cross(b - a, c - a);
}

inline int sgn(int64_t val) {
    return (val > 0) - (val < 0);
}

// Returns true iff point p lies on closed segment AB
inline bool on_segment(const Point& a, const Point& b, const Point& p) {
    return cross(a, b, p) == 0 && dot(a - p, b - p) <= 0;
}

// Exact closed segment intersection between AB and CD
bool segments_intersect(const Point& a, const Point& b,
                        const Point& c, const Point& d) {
    int s1 = sgn(cross(a, b, c));
    int s2 = sgn(cross(a, b, d));
    int s3 = sgn(cross(c, d, a));
    int s4 = sgn(cross(c, d, b));

    // Proper intersection: C,D strictly on opposite sides of AB and vice versa
    if (s1 * s2 < 0 && s3 * s4 < 0) return true;

    // Collinear / endpoint touching cases
    if (s1 == 0 && on_segment(a, b, c)) return true;
    if (s2 == 0 && on_segment(a, b, d)) return true;
    if (s3 == 0 && on_segment(c, d, a)) return true;
    if (s4 == 0 && on_segment(c, d, b)) return true;
    return false;
}

// Returns 2 * Area of simple polygon P (always an exact integer!)
int64_t polygon_twice_area(const std::vector<Point>& poly) {
    int64_t sum = 0;
    const std::size_t n = poly.size();
    for (std::size_t i = 0; i < n; ++i) {
        sum += cross(poly[i], poly[(i + 1) % n]);
    }
    return sum < 0 ? -sum : sum;
}

Production Pitfall — Using atan2 for Polar Angle Sorting

Sorting points or vectors around an origin by calling std::atan2(y, x) is both slow (sim40sim 40sim40 CPU cycles per transcendental evaluation) and inaccurate for integer coordinates near 10910^9109 where distinct rays have identical double angles. Instead, partition vectors by half-plane (half(p) = (p.y > 0 || (p.y == 0 && p.x > 0)) ? 0 : 1) and sort within each half-plane using exact cross products cross(u, v) > 0!

Key Takeaways

The 2D cross product cross(A, B, C) = (B - A) x (C - A) computes twice the signed area of triangle ABC: positive for CCW (left turn), negative for CW (right turn), and zero for collinear points.
Point P lies on closed segment AB iff cross(A, B, P) == 0 (collinear) and dot(A - P, B - P) <= 0 (between endpoints).
Always pass cross products through sgn(x) in {-1, 0, +1} before multiplying orientation signs so int64_t never overflows.
The Shoelace Formula sums P_i x P_{i+1} around a polygon boundary to compute 2 * Area as an exact integer without floating-point arithmetic.
