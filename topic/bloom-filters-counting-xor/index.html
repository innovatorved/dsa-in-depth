Intuition first

Suppose an LSM-tree storage engine (RocksDB / Cassandra) must check whether a key qqq exists across 202020 immutable on-disk SSTables. Storing an exact key index in RAM for 10910^9109 keys requires ≥16 GB\ge 16\text{ GB}≥16 GB, whereas reading disk costs milliseconds per SSTable. A Bloom Filter (Burton Bloom, 1970) sacrifices a tiny, tunable one-sided error (false positive rate ε\varepsilonε, zero false negatives) to compress set membership down to 1.44log⁡2(1/ε)1.44 \log_2(1/\varepsilon)1.44log2​(1/ε) bits per element—requiring just 9.6 bits per key (1.2 GB1.2\text{ GB}1.2 GB for 10910^9109 keys) for a 1%1\%1% false positive rate!

Modern filter engineering pushes past classic Bloom filters in two directions: Cuckoo Filters (Fan et al., 2014) store compact fff-bit fingerprints inside a bucketized Cuckoo table to support O(1)O(1)O(1) deletions and 2-cache-line locality, while Xor Filters (Graf & Lemire, 2020) solve a random 3-hypergraph peeling system over static sets to reach 1.23log⁡2(1/ε)1.23 \log_2(1/\varepsilon)1.23log2​(1/ε) bits per key with strictly 3 parallel memory reads.

p0=(1−1m)kn≈e−kn/mp_0 = \left(1 - \frac{1}{m}\right)^{kn} \approx e^{-kn/m}p0​=(1−m1​)kn≈e−kn/m

Hardware Reality: Cache-Line Blocked Bloom Filters & AVX2 Register Masks

A textbook Bloom filter spanning 128 MB128\text{ MB}128 MB with k=7k = 7k=7 hash functions performs up to 7 independent DRAM cache misses (~450 ns) on every positive query. Production storage engines (RocksDB, Apache Parquet, DuckDB) use Cache-Line Blocked (or Register-Blocked) Bloom Filters (Putze et al.): the first hash selects a single 64-byte (512-bit) cache line, and all kkk bits are set/tested inside that single 512-bit block! Even better, Parquet's Split Block Bloom Filter tests k=8k=8k=8 bits across eight 32-bit lanes in a single AVX2 _mm256_testc_si256 instruction (1 cache miss + 3 CPU cycles total).

// C++20: 64-Byte Cache-Line Blocked Bloom Filter (1 Cache Miss per Query)
#include <vector>
#include <array>
#include <cstdint>

class BlockedBloomFilter {
    struct alignas(64) CacheLineBlock {
        std::array<uint64_t, 8> words{}; // 512 bits = 64 bytes (1 L1 cache line)
    };

    std::vector<CacheLineBlock> blocks_;
    uint32_t k_;

    static uint64_t mix64(uint64_t x) noexcept {
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9ULL;
        x = (x ^ (x >> 27)) * 0x94d049bb133111ebULL;
        return x ^ (x >> 31);
    }

public:
    explicit BlockedBloomFilter(size_t numElements, uint32_t bitsPerKey = 10)
        : blocks_((numElements * bitsPerKey + 511) / 512),
          k_(static_cast<uint32_t>(bitsPerKey * 0.693147)) {
        if (blocks_.empty()) blocks_.resize(1);
        if (k_ < 1) k_ = 1;
    }

    void insert(uint64_t key) noexcept {
        uint64_t h = mix64(key);
        size_t blkIdx = ((h >> 32) * blocks_.size()) >> 32; // Lemire FastRange block select
        uint32_t h1 = static_cast<uint32_t>(h);
        uint32_t h2 = static_cast<uint32_t>(mix64(h));

        auto& blk = blocks_[blkIdx];
        for (uint32_t i = 0; i < k_; ++i) {
            uint32_t bit = (h1 + i * h2) & 511U;
            blk.words[bit >> 6] |= (1ULL << (bit & 63U));
        }
    }

    bool possiblyContains(uint64_t key) const noexcept {
        uint64_t h = mix64(key);
        size_t blkIdx = ((h >> 32) * blocks_.size()) >> 32;
        uint32_t h1 = static_cast<uint32_t>(h);
        uint32_t h2 = static_cast<uint32_t>(mix64(h));

        const auto& blk = blocks_[blkIdx];
        for (uint32_t i = 0; i < k_; ++i) {
            uint32_t bit = (h1 + i * h2) & 511U;
            if ((blk.words[bit >> 6] & (1ULL << (bit & 63U))) == 0) {
                return false; // 100% Guaranteed Negative!
            }
        }
        return true;
    }
};

Failure Modes & Adversarial Pitfalls

  • Deleting a Non-Existent Key from a Cuckoo Filter or Counting Bloom Filter: Calling delete(x) on a key xxx that was never inserted into the filter will corrupt the filter by deleting a colliding key's fingerprint (or decrementing a shared counter to 000), causing **false negatives** for legitimate keys! Only delete keys confirmed to exist in the backing store.
  • Zero Fingerprint Trap in Cuckoo Filters: If fp == 0 is used as the EMPTY slot sentinel in a Cuckoo Filter, the fingerprint function must remap 0 to 1 (fp = raw_fp ? raw_fp : 1), and h2(fp)h_2(\text{fp})h2​(fp) must be hashed before XORing so that h2(fp) != 0 (otherwise i1⊕0=i1i_1 \oplus 0 = i_1i1​⊕0=i1​, collapsing both candidate buckets into one).

Concept Check Optimal Hash Function Count in Standard Bloom Filters recall

You allocate a standard Bloom filter with mmm bits to store nnn expected distinct keys (m/nm/nm/n bits per key).

Taking the derivative of ln((1 - e^{-kn/m})^k) with respect to k shows the global minimum occurs when e^{-kn/m} = 1/2, i.e., exactly half the bits in the filter are set to 1. Solving for k gives k = (m/n) ln 2, yielding the optimal false positive rate (1/2)^k ≈ (0.6185)^{m/n}.
Concept Check Sizing a LSM-Tree SSTable Bloom Filter for 1% False Positives apply

A storage engine compacts an SSTable containing n=1,000,000n = 1{,}000{,}000n=1,000,000 keys and requires a Bloom filter false positive rate ε≤0.01\varepsilon \le 0.01ε≤0.01 (1%).

For ε = 0.01, log₂(100) ≈ 6.644. Multiplying by 1.44 gives 1.44 × 6.644 ≈ 9.58 bits per key (conventionally rounded to 10 bits/key in RocksDB/LevelDB). The optimal number of hash functions is k = 9.58 × ln(2) ≈ 6.64 → 7 probes.
Concept Check Why Deleting from a Standard Bloom Filter is Unsound apply

An engineer attempts to support key deletion in a standard bit-array Bloom filter by clearing the kkk bit positions h1(x),…,hk(x)h_1(x), \dots, h_k(x)h1​(x),…,hk​(x) back to `0` when key xxx is removed.

Multiple inserted keys can set the same bit index to 1. If deleting x resets bit h_i(x) to 0 while another inserted element y also hashed to h_i(y) = h_i(x), subsequent queries for y will see a 0 at that index and falsely report that y is absent (a false negative). Supporting deletion requires Counting Bloom Filters (4-bit counters), Cuckoo filters, or ribbon/XOR filters rebuilt on immutable snapshots.
Concept Check Cache-Line Blocked Bloom Filters vs Xor Filters in Production staff

A standard Bloom filter with k=7k = 7k=7 probes into a 16 MB16\text{ MB}16 MB bit array suffers up to 777 L3/DRAM cache misses on a positive lookup.

A cache-line Blocked Bloom filter uses the first hash to select a 64-byte cache line and sets all k bits within that single cache line (checkable in 1 memory access and a single AVX2 _mm256_testc_si256 instruction), trading slightly higher variance in bucket load (~20-30% space overhead). Key Takeaways

A Bloom filter achieves false positive rate ε using m/n = 1.44 log₂(1/ε) bits per element (~9.6 bits/key for 1% FPR) with k = (m/n) ln 2 hash functions and zero false negatives.
Kirsch-Mitzenmacher double hashing generates all k probe indices as (h1(x) + i·h2(x)) mod m from a single 64-bit hash with zero loss in asymptotic accuracy.
Cache-Line Blocked Bloom Filters confine all k bit probes to a single 64-byte L1 cache line, reducing query cost from k DRAM misses to 1 DRAM miss.
Cuckoo Filters support O(1) deletion via partial-key XOR relocation (i2 = i1 ^ h2(fp)), while static Xor Filters achieve 1.23 log₂(1/ε) bits per key with 3 parallel memory reads.
