Production Case Study: How V8 Optimizes JS Arrays (SMI, Double & Holey Elements)

7 min read Module 1.1: Asymptotic Analysis, Recurrences & Memory Hierarchy Updated Oct 23, 2026
📄 Cheat Sheet
CSSConf Australia (Mathias Bynens) V8 Internals for JavaScript Developers — Elements Kinds & Hidden Classes Watch on YouTube ↗

V8 core engineer Mathias Bynens explains how V8 tracks Elements Kinds on hidden classes and why creating array holes or mixing types triggers irreversible lattice transitions.

Intuition first

According to the ECMAScript specification, a JavaScript Array is merely a dynamic dictionary mapping stringified integer properties ("0", "1") to arbitrary boxed values, complete with Array.prototype inheritance chains. If Chrome's V8 engine actually implemented const a = [1, 2, 3] as a hash map of heap-allocated boxed numbers, numerical array processing in JavaScript and Node.js would run $50\times$ slower than C++.

Instead, V8 attaches an internal Elements Kind tag to every array's Hidden Class (Map), dynamically storing homogenous arrays as raw, unboxed C++ contiguous buffers (PACKED_SMI_ELEMENTS and PACKED_DOUBLE_ELEMENTS)—and transitions along a strict one-way lattice the moment your code introduces a floating-point number, an object reference, or an out-of-bounds "hole".

Inside V8's Elements Kinds Lattice: SMI, Double & Tagged Pointers

To execute array loops at near-native C++ speeds while preserving full ECMAScript semantics, V8 classifies the backing store of every JSArray along two orthogonal dimensions:

  1. Payload Representation (SMI vs DOUBLE vs Generic ELEMENTS):
    • SMI_ELEMENTS (Small Integers): Stores 31-bit signed integers (on 64-bit V8 with pointer compression) directly inside the backing store as immediate tagged words (least significant bit 0), requiring zero heap box allocations.
    • DOUBLE_ELEMENTS (Unboxed IEEE-754 float64): As soon as you push 3.14 or NaN into an SMI array, V8 reallocates the backing store into a contiguous C++ double[] array (8 bytes per element) so TurboFan can emit raw SSE/AVX floating-point instructions without pointer dereferencing.
    • ELEMENTS (Tagged Object Pointers): Pushing a string, object, or function forces V8 to box all numbers and store an array of tagged heap pointers—reintroducing pointer chasing!
  2. Density Invariant (PACKED vs HOLEY):
    • PACKED_*: Guarantees that every index $i \in [0, \text{length} - 1]$ contains an initialized value. Reading a[i] requires only a single bounds check i < a.length and a direct memory load.
    • HOLEY_*: Created when you allocate new Array(1000), write past the end a[10] = 1, or execute delete a[2]. Uninitialized slots contain a special sentinel (the_hole). Because JavaScript mandates that reading a missing property must walk up Array.prototype and Object.prototype, reading the_hole in a HOLEY array forces V8 to check prototype guards or bail out of JIT fast paths!

Formal Specification: The Irreversible Lattice Monotonicity Invariant

Transitions in V8's Elements Kind lattice are strictly one-way (monotonic toward more general types):

$$\texttt{PACKED\_SMI} \longrightarrow \texttt{PACKED\_DOUBLE} \longrightarrow \texttt{PACKED\_ELEMENTS}$$

$$\downarrow \hspace{9.5em} \downarrow \hspace{9.5em} \downarrow$$

$$\texttt{HOLEY\_SMI} \;\longrightarrow\; \texttt{HOLEY\_DOUBLE} \;\longrightarrow\; \texttt{HOLEY\_ELEMENTS} \longrightarrow \texttt{DICTIONARY}$$

Why does V8 never transition backwards (e.g., from HOLEY_SMI back to PACKED_SMI after all holes are filled, or from PACKED_DOUBLE back to PACKED_SMI after popping the float)? Because checking whether all $N$ elements are integers or hole-free on every mutation would turn an $O(1)$ array write into an $O(N)$ scan, and oscillating states would cause infinite JIT deoptimization loops in TurboFan!

Hardware Reality: Why PACKED_DOUBLE to PACKED_ELEMENTS Copies the Entire Array

Unlike transitioning from PACKED_SMI to HOLEY_SMI (which only updates the Hidden Class Map metadata pointer because both store 32-bit/64-bit tagged words), transitioning from PACKED_DOUBLE_ELEMENTS to PACKED_ELEMENTS (e.g., pushing "hello" or undefined into a float array) changes the physical bit-pattern of every slot from raw 64-bit IEEE-754 floats to tagged heap pointers! V8 must immediately allocate $N$ separate HeapNumber objects on the V8 heap and copy all $N$ floats into them—turning a single .push() call into an unexpected $O(N)$ allocation and GC pressure spike.

Writing V8-Friendly High-Performance JavaScript & TypedArrays

The JavaScript patterns below demonstrate how to preserve PACKED elements kinds and when to bypass V8's lattice entirely using Float64Array / Int32Array.

// V8 Performance Engineering: Avoiding Irreversible Lattice Degradations

// 1. ANTI-PATTERN: Pre-allocating with new Array(N) permanently brands the array
// as HOLEY_SMI_ELEMENTS, even after you fill every single slot!
function sumHoleyAntiPattern(n) {
  const arr = new Array(n); // Immediate transition to HOLEY_SMI_ELEMENTS!
  for (let i = 0; i < n; i++) arr[i] = i;
  let sum = 0;
  for (let i = 0; i < arr.length; i++) sum += arr[i];
  return sum;
}

// 2. PRODUCTION PATTERN A: Start with [] (PACKED_SMI_ELEMENTS) and push sequentially,
// OR for fixed-size numeric buffers, use TypedArrays (Int32Array / Float64Array)
// which CANNOT become holey and CANNOT box elements!
function sumPackedOrTyped(n) {
  const vec = new Int32Array(n); // Guaranteed contiguous unboxed 32-bit ints (16 per cache line)
  for (let i = 0; i < n; i++) vec[i] = i;
  let sum = 0;
  for (let i = 0; i < vec.length; i++) sum += vec[i];
  return sum;
}

// 3. ANTI-PATTERN: Storing -0 or NaN or undefined in an integer counter array
// Note: In V8, -0 cannot be represented as an SMI (because 0 is already an SMI),
// so arr.push(-0) silently transitions PACKED_SMI_ELEMENTS -> PACKED_DOUBLE_ELEMENTS!

Failure Modes & Adversarial Pitfalls

  • Out-of-Bounds Reads (i <= arr.length) Trigger Prototype Chain Walks: Accidentally writing for (let i = 0; i <= arr.length; i++) reads arr[arr.length] on the final iteration, which returns undefined only after V8 checks the NoElementsProtector cell or walks Array.prototype and Object.prototype. Never read past arr.length - 1 to terminate a loop!
  • Mutating Array.prototype Deoptimizes Every HOLEY Array in the Entire Process: V8 uses a global speculation guard called the NoElementsProtector to skip prototype walks on HOLEY array reads, assuming Array.prototype has no indexed properties. If any third-party library executes Array.prototype[0] = "poison", V8 permanently invalidates the global protector for the lifetime of the V8 Isolate, slowing down every HOLEY array access across the entire application!

An array `arr` of `N = 1,000,000` floating-point numbers currently has V8 kind `PACKED_DOUBLE_ELEMENTS` (stored as an unboxed 8 MB `double[]` buffer). What physical memory work must V8 perform if you execute `arr.push(null)`?

Concept Check Global `Array.prototype` Poisoning & V8's `NoElementsProtector` staff

Why does reading an element from a `HOLEY` array in V8 normally avoid walking `Array.prototype` and `Object.prototype`, and what happens across the entire V8 Isolate if any script executes `Array.prototype[0] = 'fallback'`?

By ECMAScript rules, if `arr[i]` is a hole (`!(i in arr)`), property lookup must consult `Array.prototype[i]` and `Object.prototype[i]`. V8 elides this expensive prototype chain walk via the global `NoElementsProtector` cell—until any code defines an indexed property on `Array.prototype` or `Object.prototype`, which deoptimizes all `HOLEY` array fast paths.

Why does reading an element from a `HOLEY` array in V8 normally avoid walking `Array.prototype` and `Object.prototype`, and what happens across the entire V8 Isolate if any script executes `Array.prototype[0] = 'fallback'`?

By ECMAScript rules, if `arr[i]` is a hole (`!(i in arr)`), property lookup must consult `Array.prototype[i]` and `Object.prototype[i]`. V8 elides this expensive prototype chain walk via the global `NoElementsProtector` cell—until any code defines an indexed property on `Array.prototype` or `Object.prototype`, which deoptimizes all `HOLEY` array fast paths.

Key Takeaways

V8 tracks each JSArray's layout via an Elements Kind lattice along two axes: Payload (SMI, DOUBLE, Generic Tagged Elements) and Density (PACKED vs HOLEY).
Lattice transitions are strictly one-way (irreversible): new Array(N) starts as HOLEY_SMI_ELEMENTS and can never become PACKED_SMI_ELEMENTS even after every slot is filled.
Pushing -0 or a float into a PACKED_SMI array reallocates it as PACKED_DOUBLE; pushing an object into PACKED_DOUBLE boxes all N numbers on the heap.
For numeric DSA workloads in JavaScript/TypeScript, Int32Array and Float64Array bypass the Elements Kind lattice completely, guaranteeing contiguous unboxed cache-line storage.
