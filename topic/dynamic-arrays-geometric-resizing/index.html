Intuition first

A dynamic array provides O(1)O(1)O(1) amortized random access and O(1)O(1)O(1) amortized append by allocating a contiguous block of heap memory and growing its capacity geometrically by a constant factor k>1k > 1k>1. Contiguous Representation and Geometric Growth

At the machine level, a dynamic array (such as C++ std::vector<T>, Rust Vec<T>, or Java ArrayList<E>) is a 24-byte header struct stored on the stack or inline within an object: a base pointer T* data, a current element count size_t size, and an allocated slot count size_t capacity. Whenever size < capacity, appending an element writes directly to data[size++] in a single store instruction with zero allocator interaction.

When size == capacity, the container must allocate a new contiguous region of capacity ⌈k⋅C⌉\lceil k \cdot C \rceil⌈k⋅C⌉, move or copy the existing CCC elements into the new region, destroy the old elements (if non-trivially destructible), and free the old block. If the array grew arithmetically by a constant ccc (e.g., adding 100 slots each time), appending NNN elements would copy c+2c+3c+⋯+N=Θ(N2)c + 2c + 3c + \dots + N = \Theta(N^2)c+2c+3c+⋯+N=Θ(N2) elements, yielding Θ(N)\Theta(N)Θ(N) amortized cost per append. Geometric growth by k>1k > 1k>1 ensures that reallocation distances grow exponentially, bounding total copies to a geometric series:

∑i=0⌊log⁡kN⌋ki=k⌊log⁡kN⌋+1−1k−1≤kN−1k−1=Θ(N)\sum_{i=0}^{\lfloor \log_k N \rfloor} k^i = \frac{k^{\lfloor \log_k N \rfloor + 1} - 1}{k - 1} \le \frac{k N - 1}{k - 1} = \Theta(N)i=0∑⌊logk​N⌋​ki=k−1k⌊logk​N⌋+1−1​≤k−1kN−1​=Θ(N)

Dividing by NNN insertions yields 1+kk−1=O(1)1 + \frac{k}{k - 1} = O(1)1+k−1k​=O(1) amortized work per append. Notice the trade-off embedded in kk−1\frac{k}{k - 1}k−1k​: as kkk decreases toward 111, wasted slack memory (k−1)N(k - 1)N(k−1)N shrinks, but the copy multiplier 1k−1\frac{1}{k - 1}k−11​ explodes (for k=2k = 2k=2, at most 2N2N2N copies occur; for k=1.5k = 1.5k=1.5, at most 3N3N3N copies occur; for k=1.1k = 1.1k=1.1, 11N11N11N copies occur).

Hardware Reality: Trivially Relocatable Types, realloc, and Page Table Remapping

In C++, std::vector cannot blindly call C's realloc() on arbitrary objects because C++ types may contain internal self-referential pointers (such as std::string's Small String Optimization buffer pointer in libstdc++). However, if a type is trivially copyable (or marked FollyIsRelocatable), expansion uses vectorized AVX-512 memcpy at L1/DRAM bandwidth speeds. Even better, when a dynamic array exceeds the mmap threshold (typically 128 KB in glibc ptmalloc), calling mremap() on Linux grows the allocation in O(1)O(1)O(1) physical memory operations by simply rewiring virtual page table entries (PTEs) to a new virtual address range without copying a single byte of physical DRAM!

Production Implementation: Aligned 1.5× Vector with Strong Exception Guarantee

C++2064 lines
#include <cstdlib>
#include <cstring>
#include <memory>
#include <new>
#include <type_traits>
#include <utility>

template <typename T>
class FbStyleVector {
  T* data_ = nullptr;
  std::size_t size_ = 0;
  std::size_t cap_ = 0;

  static std::size_t next_capacity(std::size_t current) noexcept {
    if (current == 0) return 4;
    if (current < 64) return current * 2;
    // 1.5x growth (k = 1.5 < phi) enables coalesced heap reuse
    return current + (current >> 1);
  }

  void grow() {
    const std::size_t new_cap = next_capacity(cap_);
    T* new_data = static_cast<T*>(::operator new(new_cap * sizeof(T), std::align_val_t{alignof(T)}));

    if constexpr (std::is_trivially_copyable_v<T>) {
      if (size_ > 0) {
        std::memcpy(new_data, data_, size_ * sizeof(T));
      }
    } else if constexpr (std::is_nothrow_move_constructible_v<T>) {
      std::uninitialized_move_n(data_, size_, new_data);
      std::destroy_n(data_, size_);
    } else {
      // Strong exception guarantee: copy first; if an exception is thrown,
      // destroy already-copied elements in new_data and leave data_ intact.
      std::size_t constructed = 0;
      try {
        for (; constructed < size_; ++constructed) {
          std::construct_at(new_data + constructed, data_[constructed]);
        }
      } catch (...) {
        std::destroy_n(new_data, constructed);
        ::operator delete(new_data, std::align_val_t{alignof(T)});
        throw;
      }
      std::destroy_n(data_, size_);
    }

    if (data_) {
      ::operator delete(data_, std::align_val_t{alignof(T)});
    }
    data_ = new_data;
    cap_ = new_cap;
  }

public:
  void push_back(const T& value) {
    if (size_ == cap_) grow();
    std::construct_at(data_ + size_, value);
    ++size_;
  }

  std::size_t size() const noexcept { return size_; }
  std::size_t capacity() const noexcept { return cap_; }
};
Production Pitfall: Missing noexcept on Move Constructors & Reference Invalidation

Two bugs routinely cripple C++ std::vector performance and safety in production:

  1. Missing noexcept on custom Move Constructors: Because std::vector::push_back guarantees the Strong Exception Guarantee (if reallocation fails partway, the vector remains unchanged), std::move_if_noexcept refuses to call a throwing move constructor during resize—falling back to deep copy construction of every element! Always mark move constructors and move assignment operators noexcept.
  2. Self-Aliasing in v.push_back(v[0]): If size == capacity, reallocating must construct the new element before freeing the old buffer, or passing an element reference from inside the vector itself will read from freed memory (use-after-free).

Concept Check Self-Referential Aliasing During v.push_back(v[0]) staff

You are implementing a custom `Vector<T>::push_back(const T& val)` method. A caller executes `vec.push_back(vec[0])` at the exact moment when `vec.size() == vec.capacity()`.

Because `val` is a `const T&` reference pointing directly to `this->data_[0]`, destroying and deallocating `data_` before reading `val` to construct `new_data[size_]` causes `new_data[size_]` to be copy-constructed from a destroyed, freed object! Production vectors always construct the new element in `new_data` before destroying/freeing `data_`.

Key Takeaways

Geometric growth by factor k > 1 bounds total copies over N appends to kN/(k - 1), achieving O(1) amortized append time.
A 2x growth factor guarantees that the newly requested allocation is strictly larger than the sum of all previously freed buffers (2^m > 2^m - 1), preventing in-arena coalesced reuse.
Any growth factor k < phi (approx 1.618), such as k = 1.5, allows the allocator to satisfy future expansions by coalescing the vector's own previously freed memory chunks.
In C++, std::vector only moves elements during reallocation if the element's move constructor is marked noexcept; otherwise it falls back to O(N) deep copies to preserve the Strong Exception Guarantee.
