Composing Hash Maps + Doubly Linked Lists: O(1) LRU & LFU Caches

6 min read Module 1.3: Linked Structures, Monotonic Stacks/Queues & Cache-Conscious Lists Updated Oct 18, 2026
📄 Cheat Sheet
NeetCode LRU & LFU Cache Design: Hash Maps + Doubly Linked Lists Watch on YouTube ↗

Intuition first

No single primitive data structure supports both $O(1)$ key lookup and $O(1)$ recency/frequency reordering: a hash table has no ordering, and a linked list requires $O(N)$ search. By cross-linking a Hash Map (key -> Node*) directly into an intrusive Circular Doubly Linked List (for LRU) or a Hash Map of Frequency-Bucket Lists tracking min_freq (for LFU), every get, put, promotion, and eviction executes in worst-case $O(1)$ time.

0:00 / 3:23

Data Structure Composition: Why Hash Map + Doubly Linked List?

In an LRU (Least Recently Used) cache of capacity $C$:

  • get(key) must look up the key in $O(1)$ time and move its entry to the Most Recently Used (MRU) head of the recency order in $O(1)$ time.
  • put(key, val) must insert or update the key at the MRU head in $O(1)$ time, and if size exceeds $C$, evict the Least Recently Used (LRU) tail entry in $O(1)$ time.
Why must the recency list be doubly linked rather than singly linked? Because when a cache hit occurs on an arbitrary interior node $u$ via the hash map (map[key] -> u), unlinking $u$ from its current position requires modifying $u$'s predecessor (u->prev->next = u->next). Without a prev pointer, finding $u$'s predecessor would take $O(N)$ time!

Algorithmic Invariant: Why O(1) LFU Cache Tracks min_freq Without a Min-Heap

In an LFU (Least Frequently Used) cache, eviction removes the item with the smallest access count freq (breaking ties by Least Recently Used among items of that same freq). Using a Min-Heap of frequencies would cost $O(\log C)$ per access. In 2010, Shah, Mitra, and Matani proved how to achieve strictly $O(1)$ LFU by grouping nodes into a hash map of doubly linked lists indexed by frequency (freq_lists[f]) and maintaining a single scalar integer min_freq:

  1. On put(new_key) (after evicting freq_lists[min_freq].back() if full): The new key starts with frequency $1$, so we insert it into freq_lists[1] and set min_freq = 1 in $O(1)$ time!
  2. On get(key) or updating an existing key of frequency $f$: We unlink the node from freq_lists[f] and push it to the MRU front of freq_lists[f + 1]. What if $f == \text{min\_freq}$ and freq_lists[f] just became empty? Then the node we just promoted was the last item at min_freq, and its new frequency is $f + 1$—so we simply increment ++min_freq in $O(1)$ time!

Because frequency only ever jumps to $1$ (on new insert) or increments by $+1$ (on access), min_freq never needs to search for the next minimum!

Hardware Reality: Multi-Core Lock Contention on the LRU Head Pointer

In a multi-threaded server with 64 CPU cores, textbook strict LRU is a scalability disaster: even on a 100% read-only workload, every get(key) cache hit mutates the doubly linked list's head pointers—requiring an exclusive mutex lock and causing L1 cache-line bouncing (MESI invalidation storms) on the sentinel node across all 64 cores! Production systems solve this in three ways:

  1. Sharded Caches (RocksDB BlockCache): Partition keys by hash prefix into 64 independent LRU shards, reducing lock contention by $64\times$.
  2. CLOCK / Approximate LRU (Linux Page Cache, Redis): Only set an atomic 1-bit reference flag on read hits (or sample 5 random keys at eviction time in Redis) so read hits never mutate linked list pointers.
  3. Deferred Ring-Buffer Replay (Java Caffeine): Record read hits into lock-free per-thread ring buffers and replay promotions asynchronously in batches.

Production Implementation: Contiguous Arena-Backed O(1) LRU Cache

C++20
#include <cstdint>
#include <unordered_map>
#include <vector>

// High-locality O(1) LRU Cache using a pre-allocated Node pool (0 mallocs after construction!)
class FastLRUCache {
  struct Node {
    int key = 0;
    int value = 0;
    int prev = 0;
    int next = 0;
  };

  int cap_;
  std::vector<Node> pool_; // Index 0 is the circular dummy sentinel!
  std::vector<int> free_list_;
  std::unordered_map<int, int> index_map_;

  void unlink(int u) noexcept {
    const int p = pool_[u].prev;
    const int n = pool_[u].next;
    pool_[p].next = n;
    pool_[n].prev = p;
  }

  void push_mru_front(int u) noexcept {
    const int first = pool_[0].next;
    pool_[u].prev = 0;
    pool_[u].next = first;
    pool_[first].prev = u;
    pool_[0].next = u;
  }

public:
  explicit FastLRUCache(int capacity) : cap_(capacity), pool_(capacity + 1) {
    pool_[0].prev = 0;
    pool_[0].next = 0;
    free_list_.reserve(capacity);
    for (int i = capacity; i >= 1; --i) {
      free_list_.push_back(i);
    }
    index_map_.reserve(capacity * 2);
  }

  int get(int key) noexcept {
    auto it = index_map_.find(key);
    if (it == index_map_.end()) return -1;
    const int u = it->second;
    unlink(u);
    push_mru_front(u);
    return pool_[u].value;
  }

  void put(int key, int value) {
    if (cap_ <= 0) return;
    auto it = index_map_.find(key);
    if (it != index_map_.end()) {
      const int u = it->second;
      pool_[u].value = value;
      unlink(u);
      push_mru_front(u);
      return;
    }

    int u = 0;
    if (!free_list_.empty()) {
      u = free_list_.back();
      free_list_.pop_back();
    } else {
      // Reuse the LRU victim node at pool_[0].prev directly without freeing!
      u = pool_[0].prev;
      unlink(u);
      index_map_.erase(pool_[u].key);
    }

    pool_[u].key = key;
    pool_[u].value = value;
    push_mru_front(u);
    index_map_[key] = u;
  }
};
Production Pitfall: Forgetting to Store key Inside the Doubly Linked List Node

When designing an LRU or LFU cache, developers frequently store only value inside the doubly linked list Node (since key is already stored in the hash map). Then, when the cache reaches capacity and selects the LRU tail node Node* victim = sentinel.prev for eviction, they realize they have no way to remove the victim from index_map_ in $O(1)$ time without knowing victim->key! Every doubly linked list node in an LRU/LFU cache must store both key and value.

Check yourself Question 1 of 4
Concept Check $O(1)$ LFU `minFreq` Maintenance Rule recall

In the $O(1)$ LFU cache algorithm (Shah, Mitra, & Matani), we maintain a hash map from `key -> Node`, a hash map of frequency buckets `freq -> DoublyLinkedList`, and an integer `minFreq`. When a key currently at frequency $f$ is accessed (`get` or `put` update), it is moved from bucket $f$ to bucket $f + 1$. Under what exact condition does `minFreq` change?

Because a node's frequency only ever increases by $+1$ per access, if bucket `minFreq` becomes empty due to an access, the node that was just promoted to `minFreq + 1` guarantees that bucket `minFreq + 1` is non-empty and is now the new minimum frequency. On insertion of a new key, its frequency is $1$, which is always the global minimum.
Concept Check Cache Pollution in Pure LRU vs Pure LFU apply

Consider two classic production workloads on a cache of capacity $C$: Workload A performs a one-time sequential table scan (`SELECT * FROM huge_table`) of $10C$ unique items. Workload B has a temporary viral event where $C$ items are requested $10^6$ times in the first hour and never requested again for the rest of the week. How do pure LRU and pure LFU fail on these two workloads?

In pure LRU, a sequential scan of $N > C$ one-time items pushes every existing hot entry out of the tail. In pure LFU without aging, items that accumulated huge historical hit counts remain pinned in the cache indefinitely, forcing all newly inserted items (with initial frequency 1) to compete for a single eviction slot.
Concept Check W-TinyLFU Admission Filter & Periodic Aging apply

In Caffeine / W-TinyLFU, how does the Count-Min Sketch track item frequencies across millions of keys in bounded memory, and how does it prevent historical frequency stagnation (Workload B)?

Because the admission filter only needs to know whether a candidate's recent frequency exceeds the victim's frequency in a cache of size $C$, 4-bit counters (0..15) suffice. Packing sixteen 4-bit counters into each `uint64_t` allows halving all counters simultaneously via `(x >> 1) & 0x7777777777777777ULL`, clearing out stale high-frequency items without clearing the sketch.
Concept Check Multi-Core Cache-Line Contention on Strict LRU Head staff

In a 64-core server handling 10 million read-heavy cache hits per second, every `get(key)` in a strict textbook LRU cache unlinks the hit node and inserts it at the shared `head` sentinel. Even if you replace the global mutex with lock-free `CAS` operations on `head.next`, throughput collapses as core count increases from 4 to 64. Why, and how do systems like Linux Page Cache, RocksDB Clock-Cache, or Memcached solve this?

In strict LRU, a logical read (`get`) performs a physical write to the global `head` sentinel's `next`/`prev` pointers. Under the MESI protocol, all 64 cores fight for Exclusive/Modified ownership of that single 64-byte cache line. Approximations like CLOCK / S3-FIFO only set an atomic `accessed = 1` bit inside the item's own cache line (if not already 1), turning repeat reads into pure shared (`S`-state) cache hits.

Why does strict LRU scale poorly on multi-socket/multi-core CPUs even on 100% read hits, and what is the systems fix?

In strict LRU, a logical read (`get`) performs a physical write to the global `head` sentinel's `next`/`prev` pointers. Under the MESI protocol, all 64 cores fight for Exclusive/Modified ownership of that single 64-byte cache line. Approximations like CLOCK / S3-FIFO only set an atomic `accessed = 1` bit inside the item's own cache line (if not already 1), turning repeat reads into pure shared (`S`-state) cache hits.

Key Takeaways

An O(1) LRU Cache composes a Hash Map (key -> Node*) with a Circular Sentinel Doubly Linked List ordered from Most Recently Used (head) to Least Recently Used (tail).
Every doubly linked list Node must store its own key alongside its value so that evicting the tail node can erase the corresponding hash map entry in O(1) time.
An O(1) LFU Cache replaces the single LRU list with a Hash Map of Doubly Linked Lists keyed by frequency, plus a scalar min_freq that resets to 1 on new inserts and increments by 1 when freq_lists[min_freq] empties.
In multi-threaded systems, strict LRU suffers from severe cache-line lock contention on read hits; production systems use sharded LRU, CLOCK bits, or W-TinyLFU with buffered replay.
