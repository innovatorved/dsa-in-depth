Algorithmic Complexity Attacks (HashDoS) & SipHash Defense

7 min read Module 2.1: Hash Tables, Modern Probing & Probabilistic Sketches Updated Oct 23, 2026
📄 Cheat Sheet
MIT OpenCourseWare MIT 6.006 Lecture 10: Open Addressing, Cryptographic Hashing Watch on YouTube ↗

Srini Devadas explains preimage resistance, second-preimage resistance, and collision resistance, establishing why unkeyed non-cryptographic hashes fail against adversarial inputs.

Intuition first

In December 2011 (28C3, Klink & Wälde, building on Crosby & Wallach 2003), security researchers demonstrated that a single 2 MB HTTP POST request containing $65{,}536$ crafted form parameter names could peg a multi-core web server's CPU at $100\%$ for 15 to 90 minutes across Java, Python, PHP, Ruby, and V8 Node.js. When a server inserts $N$ untrusted keys into a hash map whose hash function is deterministic and unkeyed (such as DJB2 h = h * 33 + c, Java String.hashCode() h = h * 31 + c, or unseeded MurmurHash), an attacker can precompute $N$ strings that all hash to the exact same bucket.

Each insertion traverses a chain (or probe cluster) of length $0, 1, 2, \dots, N-1$, executing $\sum_{i=0}^{N-1} i = \frac{N(N-1)}{2} = \Theta(N^2)$ string comparisons! Worse yet, simply adding a random seed to MurmurHash2/3 or CityHash fails because differential cryptanalysis recovers the seed or constructs universal multicollisions independent of the seed. Defeating HashDoS requires either a Cryptographic Pseudorandom Function (PRF) like SipHash-2-4 (Aumasson & Bernstein, 2012) keyed with 128 bits of CSPRNG entropy, or Treeified Chaining (Java 8+ converting chains of length $\ge 8$ into Red-Black Trees).

Anatomy of a HashDoS Attack: Equivalent Substrings & Meet-in-the-Middle

How does an attacker generate $2^{16} = 65{,}536$ colliding strings in milliseconds?

  • Equivalent Two-Char Blocks (Java hashCode / DJB2): In Java's polynomial hash $h(s) = \sum s[i] \cdot 31^{L-1-i} \bmod 2^{32}$, any two-character block $c_1 c_2$ contributes $31 c_1 + c_2$. Since 'A' * 31 + 'a' = 65 * 31 + 97 = 2112 and 'B' * 31 + 'B' = 66 * 31 + 66 = 2112, the substrings "Aa" and "BB" have the exact same hash value! Concatenating $k = 16$ choices of {"Aa", "BB"} produces $2^{16} = 65{,}536$ distinct 32-byte strings with identical hash codes in $O(1)$ effort—and because every character comparison checks the full string prefix before failing, total comparison work reaches $\Theta(N^2 \cdot L)$!
  • Seed-Independent Differential Multicollisions (MurmurHash / CityHash): Non-cryptographic hashes like MurmurHash3 and CityHash64 were designed for statistical uniformity (passing SMHasher avalanche tests), not adversarial preimage resistance. Using internal state differentials, attackers construct pairs of blocks $(\Delta_1, \Delta_2)$ that cancel each other inside the mixing rounds regardless of the 32-bit/64-bit startup seed.

Formal Specification: SipHash ARX State Machine & PRF Indistinguishability

SipHash-$c$-$d$ Architecture (Aumasson & Bernstein, 2012): Initializes four 64-bit internal state lanes $(v_0, v_1, v_2, v_3)$ by XORing a 128-bit secret key $(k_0, k_1)$ obtained from OS entropy (getrandom / /dev/urandom) with four ASCII constant words ("somepseudorandomlygeneratedbytes"). For each 8-byte message block $m_i$: set $v_3 \gets v_3 \oplus m_i$, execute $c$ compression SipRounds, and set $v_0 \gets v_0 \oplus m_i$. After the final length-padded block, set $v_2 \gets v_2 \oplus \text{0xff}$, execute $d$ finalization SipRounds, and output $v_0 \oplus v_1 \oplus v_2 \oplus v_3$.

PRF Bound: Without knowing $(k_0, k_1)$, no probabilistic polynomial-time adversary (even with adaptive timing oracle access) can distinguish SipHash-2-4 outputs from a truly random oracle, bounding $N$-key insertion cost to $O(N)$ with probability $1 - 2^{-64}$.

Hardware Reality: ARX Instructions vs SHA-256 on Short Strings

Why didn't language runtimes simply use HMAC-SHA256 for hash tables? SHA-256 processes 64-byte (512-bit) blocks with 64 rounds per block, meaning a typical 12-byte map key ("user_id_4921") wastes $80\%$ of its block capacity on padding and takes ~150 CPU cycles. SipHash-2-4 operates on 8-byte words using pure 64-bit Add-Rotate-XOR (ARX) instructions (ADD, ROL, XOR) that execute in 4 cycles per SipRound on superscalar 64-bit pipelines, completing a 16-byte string hash in ~30 cycles with zero S-box cache-timing side channels.

Production C++20 Implementation: RFC-Compliant SipHash-2-4

// C++20: Reference SipHash-2-4 (Aumasson & Bernstein) for HashDoS-Resistant Tables
#include <cstdint>
#include <cstddef>
#include <bit>
#include <cstring>

class SipHash24 {
    uint64_t k0_, k1_;

    static constexpr void sipRound(uint64_t& v0, uint64_t& v1, uint64_t& v2, uint64_t& v3) noexcept {
        v0 += v1; v1 = std::rotl(v1, 13) ^ v0; v0 = std::rotl(v0, 32);
        v2 += v3; v3 = std::rotl(v3, 16) ^ v2;
        v0 += v3; v3 = std::rotl(v3, 21) ^ v0;
        v2 += v1; v1 = std::rotl(v1, 17) ^ v2; v2 = std::rotl(v2, 32);
    }

public:
    constexpr SipHash24(uint64_t k0, uint64_t k1) noexcept : k0_(k0), k1_(k1) {}

    uint64_t operator()(const uint8_t* data, size_t len) const noexcept {
        uint64_t v0 = k0_ ^ 0x736f6d6570736575ULL;
        uint64_t v1 = k1_ ^ 0x646f72616e646f6dULL;
        uint64_t v2 = k0_ ^ 0x6c7967656e657261ULL;
        uint64_t v3 = k1_ ^ 0x7465646279746573ULL;

        const size_t blocks = len / 8;
        for (size_t i = 0; i < blocks; ++i) {
            uint64_t m = 0;
            std::memcpy(&m, data + i * 8, sizeof(uint64_t));
            v3 ^= m;
            sipRound(v0, v1, v2, v3);
            sipRound(v0, v1, v2, v3); // c = 2 compression rounds
            v0 ^= m;
        }

        // Pack remaining 0..7 bytes in little-endian + (len mod 256) in top byte [56..63]
        uint64_t last = static_cast<uint64_t>(len & 0xff) << 56;
        const uint8_t* tail = data + blocks * 8;
        for (size_t r = 0; r < (len & 7); ++r) {
            last |= static_cast<uint64_t>(tail[r]) << (r * 8);
        }

        v3 ^= last;
        sipRound(v0, v1, v2, v3);
        sipRound(v0, v1, v2, v3);
        v0 ^= last;

        v2 ^= 0xffULL;
        for (int d = 0; d < 4; ++d) sipRound(v0, v1, v2, v3); // d = 4 finalization rounds
        return v0 ^ v1 ^ v2 ^ v3;
    }
};

Failure Modes & Adversarial Pitfalls

  • Exposing Hash Iteration Order to Untrusted Clients: Even if a server uses SipHash with a random 128-bit secret key, if an API serializes hash map keys in bucket iteration order and returns them to the user, an attacker can mount a timing/ordering side-channel attack to learn which keys share buckets or recover the secret key. Keep seeds private or randomize per-table state.
  • Using Unkeyed fxhash / fnv on Network-Facing Maps: Rust's rustc-hash (FxHashMap) and C++'s std::unordered_map use fast unkeyed hashes. While FxHashMap is $2\times$ faster on integer keys inside a compiler AST, exposing it to HTTP headers, JSON keys, or query parameters invites immediate $\Theta(N^2)$ HashDoS.

Concept Check Asymptotic Complexity Degradation in a HashDoS Attack recall

When an attacker submits N crafted keys that all collide into the same hash bucket of a hash table, what does the total time complexity of inserting all N keys degrade from and to (assuming key length L = O(1))?

Inserting the i-th colliding key scans i - 1 existing entries in that bucket/cluster before appending. Summing i - 1 from i = 1 to N yields N(N - 1)/2 = Θ(N^2) comparisons.
Concept Check Java Polynomial String Hash Equivalent-Substring Multicollisions apply

Java's `String.hashCode()` computes h(s) = sum_{i} s[i] * 31^(L-1-i) mod 2^32. Given that ASCII `'A' = 65`, `'B' = 66`, and `'a' = 97`, why do `'Aa'` and `'BB'` allow an attacker to trivially generate 2^k colliding strings of length 2k?

By linearity of the polynomial hash, replacing 'Aa' with 'BB' at any aligned 2-char position contributes the exact same value 2112 * 31^p to the total sum, yielding 2^16 = 65,536 colliding 32-byte strings with zero brute-force search.
Concept Check SipHash-c-d Parameter Meaning (SipHash-2-4 vs SipHash-1-3) apply

In the family of keyed ARX pseudorandom functions `SipHash-c-d` (such as `SipHash-2-4` and Rust's default `SipHash-1-3`), what do the parameters `c` and `d` specify?

SipHash-c-d maintains four 64-bit state lanes (v0..v3) keyed by a 128-bit secret (k0, k1). It applies c SipRounds per 8-byte input word and d SipRounds during finalization.
Concept Check Why Seeded Non-Cryptographic Hashes (MurmurHash3 / CityHash) Fail Against HashDoS staff

After the 2011 HashDoS disclosures, several runtimes initially attempted to defend `MurmurHash2/3` or `CityHash` simply by initializing the hash function with a random 32-bit or 64-bit seed at process startup. Why did cryptanalysts (Jean-Philippe Aumasson, Daniel J. Bernstein, Martin Boßlet) show that this defense is broken?

Because MurmurHash and CityHash use invertible multiplication/XOR steps with too few mixing rounds between block injections, an attacker can craft block differences Δm that cancel out the internal state difference regardless of the initial seed, producing universal multicollisions.

After the 2011 HashDoS disclosures, several runtimes initially attempted to defend `MurmurHash2/3` or `CityHash` simply by initializing the hash function with a random 32-bit or 64-bit seed at process startup. Why did cryptanalysts (Jean-Philippe Aumasson, Daniel J. Bernstein, Martin Boßlet) show that this defense is broken?

Because MurmurHash and CityHash use invertible multiplication/XOR steps with too few mixing rounds between block injections, an attacker can craft block differences Δm that cancel out the internal state difference regardless of the initial seed, producing universal multicollisions.

Key Takeaways

HashDoS attacks exploit unkeyed or weak hash functions by injecting N colliding keys, turning O(N) batch insertion into Θ(N^2) comparisons and freezing server CPUs.
Simply adding a random seed to non-cryptographic hashes like MurmurHash3 or CityHash fails because differential multicollisions bypass the seed.
SipHash-2-4 is a keyed ARX Pseudorandom Function (PRF) using a 128-bit CSPRNG key, 2 compression rounds per 8-byte block, and 4 finalization rounds to guarantee O(1) expected lookups against any adversary.
Java 8+ HashMap mitigates HashDoS deterministically by converting separate chains of length ≥ 8 (when capacity ≥ 64) into Red-Black Trees with O(log N) worst-case lookup.
