LSM-Trees vs B+ Trees: MemTables, SSTables, Compaction & RUM Conjecture

7 min read Module 3.2: Self-Balancing, Augmented, Disk-Backed & Persistent Trees Updated Oct 23, 2026
📄 Cheat Sheet
ByteByteGo The Secret Sauce Behind NoSQL: Log-Structured Merge (LSM) Trees Watch on YouTube ↗

Explains the MemTable + SSTable pipeline, Size-Tiered vs Leveled Compaction in RocksDB/Cassandra, Bloom filters, and write/read/space amplification tradeoffs.

Intuition first

Why do write-intensive distributed databases like RocksDB, LevelDB, Apache Cassandra, ScyllaDB, and Pebble abandon B+ Trees in favor of Patrick O'Neil's Log-Structured Merge-Tree (LSM-Tree, 1996)? Because in a B+ Tree, every random key insertion or deletion requires reading and rewriting a random $4\text{ KB}–16\text{ KB}$ disk page in place, Bottlenecking on random disk IOPS and wearing out SSD flash cells through high Write Amplification.

An LSM-Tree turns every random write, update, and delete into a sequential append! Incoming writes go into an in-memory balanced structure (the MemTable, typically a Skip List or ART) backed by an append-only Write-Ahead Log (WAL). When the MemTable reaches capacity (e.g., $64\text{ MB}$), it is flushed sequentially to disk as an immutable Sorted String Table (SSTable) at Level $L_0$, and background Compaction threads $K$-way merge sorted SSTables across levels $L_1, L_2, \dots, L_k$ just like MergeSort!

The LSM Write/Read Pipeline, Tombstones & Compaction Strategies

Because SSTables on disk are strictly immutable, an LSM-Tree never modifies an existing file in place:

  • Updates & Deletions (Tombstones): Updating key $K$ simply appends a newer version (K, v_new, seqNo) to the MemTable. Deleting key $K$ appends a special Tombstone marker (K, TOMBSTONE, seqNo). The obsolete older record is only physically reclaimed later when a background compaction merges the SSTable containing the tombstone with the older SSTable at the bottommost level!
  • Point Lookups (MemTable $\to L_0 \to L_1 \dots \to L_k$): To read key $K$, we search the active MemTable, then immutable MemTables awaiting flush, then every overlapping $L_0$ SSTable (because $L_0$ files are raw MemTable flushes whose key ranges overlap!), and finally at most one SSTable per level $L_1 \dots L_k$ (since levels $\ge 1$ are partitioned into non-overlapping key ranges). To avoid reading SSTable blocks from disk for keys that are not present, every SSTable embeds an in-memory Bloom Filter (or Ribbon Filter) and fence-pointer sparse index!

The RUM Conjecture (Athanassoulis et al., Harvard DASlab 2016) & Leveled WA Math

Define the three fundamental amplification factors of any index structure:

$$\text{WA} = \frac{\text{Bytes Written to Storage}}{\text{Logical Bytes Inserted}}, \quad \text{RA} = \frac{\text{Bytes Read from Storage}}{\text{Logical Bytes Queried}}, \quad \text{SA} = \frac{\text{Total Storage Footprint}}{\text{Logical Dataset Size}}$$

The RUM Conjecture: No access method can simultaneously optimize Read overhead, Update (Write) overhead, and Memory (Space) overhead—minimizing any two necessarily degrades the third! Specifically, for an LSM-Tree with level size multiplier $T$ (typically $T = 10$, so $L_k = 10^k \cdot L_0$) and $L = \log_T(N / M_{\text{mem}})$ levels:

  • In Size-Tiered Compaction (STCS), $T$ runs of equal size are merged together only when all $T$ accumulate: each byte is rewritten once per level, giving $\text{WA} = O(\log_T N)$, but up to $T$ overlapping runs exist per level ($\text{SA} = O(T)$).
  • In Leveled Compaction (LCS), each level $L_i$ ($i \ge 1$) is kept strictly sorted with non-overlapping SSTables. Merging a file from $L_{i-1}$ into $L_i$ rewrites up to $T$ overlapping files in $L_i$, yielding $\text{WA} = O(T \log_T N)$, while bounding stale duplicate space to $\sum_{i=1}^{L-1} T^{-i} \approx \frac{1}{T - 1} \approx 11.1\%$ for $T=10$!

Hardware Reality: Why Range Queries Bypass Standard Bloom Filters (and How Prefix/SuRF Filters Help)

A standard Bloom Filter hashes an exact key $h(K)$, so it can answer get("user:42") by skipping 99% of SSTables, reducing a point lookup to $\le 1$ disk read. However, for a short range scan (SELECT * FROM events WHERE key BETWEEN "user:42:00" AND "user:42:99"), a standard Bloom Filter is completely useless because you cannot hash every possible string in a continuous interval! Consequently, an LSM range iterator must seek into every $L_0$ SSTable and one SSTable at every level $L_1 \dots L_k$. RocksDB mitigates this with Prefix Bloom Filters (hashing a fixed key prefix like "user:42") or Zhang et al.'s SuRF (Succinct Range Filter, SIGMOD 2018) based on Fast Succinct Tries.

Implementation: LSM Compaction Stream Merger with MVCC Sequence & Tombstone Elision

// C++20: LSM Compaction K-Way Deduplicator & Bottommost-Level Tombstone Elision
#include <vector>
#include <string>

struct LSMRecord {
    std::string key;
    std::string value;
    uint64_t seqNo;     // Monotonically increasing MVCC transaction timestamp
    bool isTombstone;   // True if this record is a DELETE marker
};

// Given sorted records from K merged SSTable runs (ordered by key ASC, then seqNo DESC),
// deduplicates shadowed versions and drops tombstones if compacting into the bottommost level.
std::vector<LSMRecord> compactSortedStream(
    const std::vector<LSMRecord>& mergedStream,
    uint64_t oldestActiveSnapshotSeq,
    bool isBottommostLevel
) {
    std::vector<LSMRecord> output;
    for (size_t i = 0; i < mergedStream.size(); ++i) {
        const auto& rec = mergedStream[i];
        // Skip older versions of the same key if shadowed by a version <= oldestActiveSnapshotSeq
        if (!output.empty() && output.back().key == rec.key &&
            output.back().seqNo <= oldestActiveSnapshotSeq) {
            continue;
        }
        // Physical deletion: only drop a tombstone when it reaches the bottommost level
        // AND no older snapshot can see past it!
        if (rec.isTombstone && isBottommostLevel && rec.seqNo <= oldestActiveSnapshotSeq) {
            continue;
        }
        output.push_back(rec);
    }
    return output;
}

Failure Modes & Adversarial Pitfalls

  • Dropping Tombstones Above the Bottommost Level Resurrects Deleted Data ("Zombie Keys"): If Compaction merges $L_1$ and $L_2$ and discards a Tombstone for key $K$ while an older version of $K$ still sits in $L_3$, subsequent reads will fall through $L_1$ and $L_2$ and return the deleted value from $L_3$! A tombstone can only be physically dropped when it reaches the bottommost level (or when Bloom/range metadata proves no SSTable at any deeper level contains $K$).
  • RocksDB Tombstone Scan Degradation ("Delete-Heavy Queue Anti-Pattern"): Using an LSM-Tree as a FIFO queue (insert at tail, delete at head, then seekToFirst()) accumulates millions of consecutive tombstones at the start of the keyspace before compaction catches up—causing seekToFirst() to scan past millions of dead tombstones in $O(N)$ time!
Check yourself Question 1 of 4
Concept Check The Write Path of an LSM-Tree Storage Engine recall

When a client executes `Put(key, value)` in an LSM-tree engine such as RocksDB, LevelDB, or Cassandra, what happens on the synchronous critical path before returning success?

LSM-trees convert random logical writes into sequential physical I/O. Every `Put` or `Delete` (tombstone) is appended sequentially to the WAL and inserted into the in-memory MemTable. Only when the MemTable reaches its size limit (e.g., 64 MB) is it frozen as an Immutable MemTable and flushed sequentially to disk as an immutable Level-0 Sorted String Table (SSTable).
Concept Check Tiered vs Leveled Compaction Trade-Offs (Write vs Space Amplification) apply

Consider an LSM-tree with growth factor $T = 10$ and $L$ levels. Compare **Size-Tiered Compaction** (used in Cassandra for write-heavy workloads) against **Leveled Compaction** (used in LevelDB/RocksDB).

In Size-Tiered Compaction, a level accumulates T sorted runs before merging them once into the next level, so each byte is rewritten only once per level (WA = O(L)), but up to T overlapping runs exist per level (high RA) and merging the largest level temporarily doubles disk usage (high SA). In Leveled Compaction, each level >= 1 is maintained as a single partitioned sorted run: merging from L_{i-1} into L_i rewrites up to T overlapping SSTables in L_i (WA = O(T * L)), but obsolete keys/tombstones live mainly in the top levels so SA is only ~1/T (~10%).
Concept Check Bloom Filter Bits-Per-Key and Point-Lookup Read Amplification apply

Suppose an LSM-tree has $K = 10$ sorted runs on disk, and a point lookup searches for a key that does not exist in the database. Each SSTable has a Bloom filter configured with $b = 10$ bits per key (false positive rate $\varepsilon \approx e^{-10 \ln^2 2} \approx 0.0082$).

By checking the in-memory Bloom filter for each candidate SSTable before reading its data blocks from disk, a point lookup avoids disk I/O with probability 1 - epsilon (~99.18% per run), reducing expected wasted I/Os across 10 runs to 0.082. However, standard Bloom filters hash exact keys; a range query `Seek(prefix)` does not know which exact keys exist in the range, so it must open iterators on all K runs (unless a prefix Bloom filter is configured for fixed-length prefixes).
Concept Check Tombstone Retention & Snapshot Isolation Bugs in Compaction staff

In an LSM-tree, deleting a key writes a **tombstone** marker `(key, seq_num, TYPE_DELETE)`. During compaction of Level $i$ into Level $i+1$, when is it legally safe for the compaction thread to garbage-collect (drop) a tombstone so it takes zero space?

Dropping a tombstone prematurely causes two classic production bugs: (1) 'Zombie data resurrection': if an older version of `key` still exists in Level i+2 and the tombstone is dropped at Level i+1, future reads will fall through to Level i+2 and resurrect the deleted value! (2) Snapshot isolation violation: if an active transaction holds a snapshot at sequence number S < tombstone.seq, dropping the tombstone and the older value it shadows would hide the value that snapshot S is entitled to see.

Identify the exact conditions required before a tombstone can be permanently dropped during compaction:

Dropping a tombstone prematurely causes two classic production bugs: (1) 'Zombie data resurrection': if an older version of `key` still exists in Level i+2 and the tombstone is dropped at Level i+1, future reads will fall through to Level i+2 and resurrect the deleted value! (2) Snapshot isolation violation: if an active transaction holds a snapshot at sequence number S < tombstone.seq, dropping the tombstone and the older value it shadows would hide the value that snapshot S is entitled to see.

Key Takeaways

LSM-Trees convert random writes, updates, and deletes into sequential appends via an in-memory MemTable + WAL that flushes immutable SSTables to disk.
Deletions write Tombstone markers; a tombstone cannot be garbage-collected until compaction reaches the bottommost level, otherwise older versions in deeper levels resurrect as zombie keys.
Leveled Compaction (RocksDB) minimizes Space Amplification (≤ 11% stale overhead) at the cost of higher Write Amplification O(T log_T N), whereas Size-Tiered Compaction (Cassandra) minimizes Write Amplification O(log_T N) at the cost of higher temporary Space Amplification.
Bloom Filters reduce LSM point-lookup Read Amplification to ~1 disk read, but standard Bloom Filters cannot prune arbitrary range scans unless paired with Prefix Bloom Filters or Succinct Range Filters (SuRF).
