Production Case Study: Inside git diff (Myers vs Patience vs Histogram Diff)

7 min read Module 4.2: Suffix Structures, Sequence Alignment & Data Compression Updated Oct 23, 2026
📄 Cheat Sheet
Tom Scott How Computers Compress Text: Huffman Coding and Huffman Trees Watch on YouTube ↗

Compares git diff --myers, --patience, and --histogram on real C/Rust refactoring commits to show how low-frequency anchor lines prevent misaligned closing braces.

Intuition first

Have you ever added a new function to a source file, run git diff, and seen Git claim that you deleted the closing brace } of the previous function and inserted the closing brace of the new function inside the old one? Mathematically, Eugene Myers' $O(ND)$ algorithm found a valid Shortest Edit Script—because every line has weight $1$, matching two boilerplate } or blank lines is worth the exact same score as matching two unique function signatures!

To produce human-readable diffs that respect semantic code structure, Bram Cohen invented Patience Diff and JGit / git diff --histogram refined it into Histogram Diff: before running Myers, anchor the diff on the lowest-frequency matching lines (such as unique function headers fn parse_header() { that occur $1$ time in both files) via Longest Increasing Subsequence (LIS), and recursively diff the regions between those anchors!

1. The Boilerplate Misalignment Problem in Pure Myers Diff

Suppose File $A$ and File $B$ differ because a developer rewrote the body of func_one() while adding func_two(). Inside those functions sit dozens of identical boilerplate lines (}, return err;, blank lines). Because pure Myers diff treats every line as an unweighted token and greedily slides along the first available diagonal snake, it readily matches the closing } of func_one() in File $A$ with the closing } of func_two() in File $B$, producing a tangled, unreadable diff hunk that splits across function boundaries.

2. Git's Three Production Diff Engines

  1. git diff --myers (Default / xdl_do_diff): Hashes each line into an integer token ID, strips common prefix/suffix lines, and runs Bidirectional Myers $O(ND)$ with Hirschberg's linear-space midpoint split (find_snake). Fast when $D$ is small, but includes heuristic cutoffs (max_chain_length) when $D$ is huge so it doesn't stall in $\Theta(N^2)$ time on completely rewritten files.
  2. git diff --patience (Bram Cohen):
    • Identify all lines that occur exactly once in File $A$ AND exactly once in File $B$.
    • Find the Longest Increasing Subsequence (LIS) of their line positions in $O(U \log U)$ time via Patience Sorting (hence the name!).
    • Use those matched unique lines as immovable structural anchors, and recursively diff the sub-slices between consecutive anchors (falling back to Myers when no unique common lines remain in a slice).
  3. git diff --histogram (JGit / Git 1.7.7+): What if a slice has no lines with count $== 1$ (e.g., a file with two similar classes where every header appears twice)? Patience Diff immediately falls back to Myers. Histogram Diff generalizes Patience Diff: it builds a frequency histogram of all lines in $A$, scans for the common line with the lowest occurrence count (up to a threshold of 64 occurrences) that forms the longest contiguous matching block, splits both files around that anchor block, and recurses on the prefix and suffix!

Patience Anchor Order-Preservation Invariant

Let $(a_1, b_1), (a_2, b_2), \dots, (a_k, b_k)$ be the pairs of line indices for lines occurring uniquely in both $A$ and $B$, sorted by $a_1 < a_2 < \dots < a_k$. A subset of these unique matches can appear together in a valid non-crossing diff alignment if and only if their $B$-indices form a strictly increasing subsequence $b_{i_1} < b_{i_2} < \dots < b_{i_m}$. Finding the Longest Increasing Subsequence (LIS) in $O(k \log k)$ time maximizes the number of preserved structural anchors.

Line Hashing & Post-Diff Slider Heuristics in libxdiff

Before running any diff algorithm, Git's libxdiff hashes every line (using a fast multiplicative hash) into a 32-bit bucket ID so the inner diff loop compares uint32_t integers in registers rather than calling memcmp on line strings. After computing the edit script, Git runs a slider post-processing pass (xdl_change_compact) that shifts ambiguous deletion/insertion hunks up or down when surrounded by identical lines (such as }) so the hunk aligns cleanly with blank lines and indentation boundaries.

4. Reference Implementation: Patience Diff Unique-Line LIS Anchor Finder

#include <algorithm>
#include <string_view>
#include <unordered_map>
#include <utility>
#include <vector>

struct AnchorMatch {
    int line_a;
    int line_b;
};

// Finds Patience Diff structural anchors: Longest Increasing Subsequence of unique common lines
std::vector<AnchorMatch> find_patience_anchors(const std::vector<std::string_view>& a,
                                               const std::vector<std::string_view>& b) {
    std::unordered_map<std::string_view, int> count_a, count_b, pos_b;
    for (int i = 0; i < static_cast<int>(a.size()); ++i) count_a[a[i]]++;
    for (int j = 0; j < static_cast<int>(b.size()); ++j) {
        count_b[b[j]]++;
        pos_b[b[j]] = j;
    }

    // Collect pairs (i, j) for lines occurring exactly once in A and once in B
    std::vector<AnchorMatch> uniques;
    for (int i = 0; i < static_cast<int>(a.size()); ++i) {
        if (count_a[a[i]] == 1 && count_b[a[i]] == 1) {
            uniques.push_back({i, pos_b[a[i]]});
        }
    }
    if (uniques.empty()) return {};

    // Patience Sorting O(U log U) Longest Increasing Subsequence on line_b
    const int u = static_cast<int>(uniques.size());
    std::vector<int> tails, tail_idx, parent(u, -1);
    for (int k = 0; k < u; ++k) {
        int y = uniques[k].line_b;
        auto it = std::lower_bound(tails.begin(), tails.end(), y);
        int idx = static_cast<int>(it - tails.begin());
        if (it == tails.end()) {
            tails.push_back(y);
            tail_idx.push_back(k);
        } else {
            *it = y;
            tail_idx[idx] = k;
        }
        if (idx > 0) parent[k] = tail_idx[idx - 1];
    }

    std::vector<AnchorMatch> anchors;
    for (int cur = tail_idx.back(); cur != -1; cur = parent[cur]) {
        anchors.push_back(uniques[cur]);
    }
    std::reverse(anchors.begin(), anchors.end());
    return anchors;
}
Patience and Histogram Diff Do Not Guarantee Minimum Edit Distance

By forcing the alignment path to pass through low-frequency structural anchors (like function declarations), Patience Diff and Histogram Diff deliberately sacrifice mathematical shortest-edit-script optimality when matching a dozen } braces across functions would save 2 lines in the diff! In version control and code review, semantic alignment of unique lines is far more valuable than saving 2 lines by scrambling function boundaries.

Check yourself Question 1 of 4
Concept Check Why Pure Myers Diff Misaligns Closing Braces `{` / `}` recall

When comparing two versions of a source file where a function was rewritten and another function was added below it, `git diff --myers` frequently pairs the old function's closing `}` with the new function's closing `}`.

Myers' algorithm optimizes solely for the unweighted Shortest Edit Script ($D = N + M - 2|\text{LCS}|$). When multiple alignments have the same (or nearly the same) LCS length, greedy diagonal extension latches onto high-frequency boilerplate lines like `}`, `else {`, or blank lines.
Concept Check Patience Diff's Unique-Line LIS Anchor Step apply

Bram Cohen's Patience Diff (`git diff --patience`) first identifies all lines that appear <strong>exactly once</strong> in File $A$ and <strong>exactly once</strong> in File $B$. Suppose these unique common lines occur at $(a_1, b_1) = (2, 8)$, $(a_2, b_2) = (5, 3)$, $(a_3, b_3) = (9, 6)$, and $(a_4, b_4) = (12, 10)$.

Since the pairs are already sorted by their File $A$ indices ($2 < 5 < 9 < 12$), any valid non-crossing alignment must select a subsequence whose File $B$ indices are strictly increasing. The LIS of $(8, 3, 6, 10)$ is $(3, 6, 10)$ of length 3.
Concept Check How Histogram Diff (`--histogram`) Improves Upon Patience Diff apply

Suppose you diff a file containing two similar test suites where every function header and setup line appears <strong>twice</strong> in File $A$ and <strong>twice</strong> in File $B$, so there are ZERO lines with frequency $== 1$.

Patience Diff's strict $\text{freq}_A == 1 \land \text{freq}_B == 1$ filter makes it brittle whenever code blocks are duplicated even once. Histogram Diff (`xdiff/xhistogram.c`) generalizes the idea to a full frequency histogram, picking the lowest-frequency anchor block with $\text{freq}_A \le 64$.
Concept Check Why Myers Diff Needs Heuristic Cutoffs (`max_chain_length`) in Production staff

Although Myers diff runs in $O((N + M)D)$ time, consider what happens when a user runs `git diff` on two 50,000-line auto-generated JSON or lockfiles that share almost no lines ($D \approx N + M = 100{,}000$).

In Myers diff, step $d$ iterates $k$ from $-d$ to $+d$ ($d + 1$ diagonals), so reaching edit distance $D$ takes $\sum_{d=0}^D (d + 1) = \Theta(D^2)$ work even without snake comparisons! When $D = \Theta(N)$, $\Theta(D^2) = \Theta(N^2)$, which is why `libxdiff` (and Histogram Diff) use effort cutoffs on highly divergent regions.

Key Takeaways

Pure Myers diff weights every line equally, so high-frequency boilerplate lines ('}', blank lines) can hijack diagonal snakes and misalign function boundaries.
Patience Diff finds the Longest Increasing Subsequence (LIS) of lines occurring exactly once in both files in O(U log U) time and recursively diffs the intervals between those anchors.
Histogram Diff generalizes Patience Diff by anchoring on the longest contiguous match containing the lowest-frequency line (up to 64 occurrences), often running faster than Myers on large diffs.
