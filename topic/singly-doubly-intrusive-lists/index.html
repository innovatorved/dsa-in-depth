Singly, Doubly & Intrusive Linked Lists (Linux Kernel list_head)

Intuition first

Standard library linked lists (std::list) invert ownership by wrapping every payload inside a separately heap-allocated node—doubling allocator traffic, fragmenting L1 cache lines, and restricting an object to one list at a time. Intrusive linked lists (like the Linux kernel's struct list_head) embed the next/prev hooks directly inside the domain struct, recovering the parent struct via compile-time offsetof pointer arithmetic (container_of) with zero dynamic allocations.

Pointer-to-Pointer (Node**) & Circular Sentinel Elimination

In a naive singly or doubly linked list, every insertion or deletion checks a special-case branch: if (prev == nullptr) head = curr->next; else prev->next = curr->next;. As Linus Torvalds famously demonstrated, there are two complementary techniques that completely eliminate special-case boundary branches:

  1. Indirect Pointer-to-Pointer (Node** pp = &head) for Singly Linked Lists: Instead of tracking a predecessor node pointer Node* prev, track the address of the pointer field that points to the current node: Node** indirect = &head. Advancing moves to indirect = &((*indirect)->next), and unlinking the target node executes *indirect = (*indirect)->next uniformly—whether the node is the head of the list or in the middle!
  2. Circular Dummy Sentinel Node for Doubly Linked Lists: By maintaining a permanent sentinel node sentinel initialized to point to itself (sentinel.next = sentinel.prev = &sentinel), the list is never physically empty. Every real node sits strictly between two valid Node structs (sentinel.next is front(), sentinel.prev is back()), reducing insert_between(prev, next, node) and unlink(node) to 4 and 2 unconditional pointer stores respectively.
Systems Invariant: Intrusive list_head & The container_of Offset Identity

In a non-intrusive list (std::list<Task>), inserting a Task allocates a separate heap node containing {prev, next, Task}, and removing a Task* given only its address is $O(N)$ unless you also store a std::list::iterator alongside it. In the Linux kernel's intrusive design, the 16-byte hook struct list_head { list_head *next, *prev; } is embedded directly as a member inside struct Task:

$$\text{addr}(\text{Task}) = \text{addr}(\text{member\_ptr}) - \text{offsetof}(\text{Task},\; \text{member})$$

Because the byte offset of a struct field is a compile-time constant known to the compiler, container_of(ptr, Task, run_list) subtracts that constant integer offset from the list_head* address—recovering the enclosing Task* in zero memory dereferences! Even better, a single Task struct can embed multiple list_head fields (run_queue, all_tasks, wait_list), participating in three doubly linked lists simultaneously with zero heap allocations.

Hardware Reality: Dependent Load Chains & Out-of-Order Execution Paralysis

Why is traversing a linked list of $N$ nodes across the heap $20\times$ to $50\times$ slower than scanning an array of $N$ elements? On a modern out-of-order CPU (with a 512-entry Reorder Buffer and 12 execution ports), an array loop computes address base + i * sizeof(T) independently for iterations $i, i+1, \dots, i+15$, issuing up to 10–12 L1/L2 memory loads in parallel (Memory-Level Parallelism, MLP). In a linked list, the address of node $k+1$ (curr = curr->next) is stored inside the payload of node $k$. The CPU cannot even know the virtual address of node $k+1$ until the load for node $k$ returns from L3/DRAM (50–250 cycles later), serializing execution to a strict MLP $= 1$ pointer-chasing stall!

Production Implementation: Intrusive Circular Doubly Linked List & Torvalds Indirect Unlink

#include <cstddef>
#include <cstdint>

// Linux-kernel style intrusive circular doubly-linked list hook
struct IntrusiveListNode {
  IntrusiveListNode* next = this;
  IntrusiveListNode* prev = this;

  void init() noexcept { next = prev = this; }
  bool empty() const noexcept { return next == this; }

  static void link_between(IntrusiveListNode* prev_node,
                           IntrusiveListNode* next_node,
                           IntrusiveListNode* new_node) noexcept {
    new_node->next = next_node;
    new_node->prev = prev_node;
    next_node->prev = new_node;
    prev_node->next = new_node;
  }

  // Insert new_node right before this (if this is sentinel head, this is push_back!)
  void push_back(IntrusiveListNode* new_node) noexcept {
    link_between(this->prev, this, new_node);
  }

  // Insert new_node right after this (if this is sentinel head, this is push_front!)
  void push_front(IntrusiveListNode* new_node) noexcept {
    link_between(this, this->next, new_node);
  }

  // Branchless O(1) self-unlink!
  void unlink() noexcept {
    next->prev = prev;
    prev->next = next;
    next = prev = this;
  }
};

// Compile-time offset arithmetic (C++ equivalent of Linux kernel container_of)
#define CONTAINER_OF(ptr, Type, member)   reinterpret_cast<Type*>(reinterpret_cast<char*>(ptr) - offsetof(Type, member))

// Linus Torvalds's branchless pointer-to-pointer singly linked list removal
struct SinglyNode {
  int val;
  SinglyNode* next;
};

void remove_first_matching(SinglyNode** head_ref, int target) noexcept {
  SinglyNode** indirect = head_ref;
  while (*indirect != nullptr) {
    if ((*indirect)->val == target) {
      *indirect = (*indirect)->next; // Works identically for head node and interior nodes!
      return;
    }
    indirect = &((*indirect)->next);
  }
}
Production Pitfall: Mutating Links While Iterating Without Saving next (list_for_each_safe)

When iterating over an intrusive or manual linked list and unlinking or freeing nodes inside the loop body, writing for (auto* pos = head.next; pos != &head; pos = pos->next) { pos->unlink(); } causes an immediate infinite loop or Use-After-Free because pos->unlink() overwrites pos->next = pos (or free(pos) poisons pos->next) before the loop increment expression reads pos->next! Always use the Linux kernel's list_for_each_safe(pos, tmp, head) idiom: cache auto* next_node = pos->next; at the very top of the loop body before mutating or freeing pos.

Check yourself Question 1 of 4
Concept Check Intrusive List Container Recovery recall

In the Linux kernel's intrusive doubly linked list (`struct list_head`), how does the `container_of(ptr, type, member)` macro recover the address of the enclosing struct from a pointer to the embedded list node?

Because the layout of `type` is fixed at compile time, `offsetof(type, member)` is a constant integer. Subtracting that constant from the char-cast pointer `ptr` yields the exact starting address of the enclosing structure in a single integer subtraction.
Concept Check Circular Sentinel Branch Elimination apply

A doubly linked list initialized with a circular dummy sentinel head sets `sentinel.next = &sentinel` and `sentinel.prev = &sentinel`. Why does this eliminate conditional branches during node insertion and deletion?

In a standard NULL-terminated doubly linked list, unlinking or inserting at the head or tail requires checking `if (node->prev != NULL)` and `if (node->next != NULL)`. A circular sentinel acts as a permanent neighbor for both the first and last elements, turning every splice into uniform pointer assignments.
Concept Check Allocation and Cache Overhead of Non-Intrusive Lists apply

Consider `std::list<uint64_t>` in C++ on a 64-bit system using `ptmalloc2` (which adds a 16-byte allocator header per `malloc` call). What is the total memory consumed per 8-byte integer stored, and why does traversal stall the CPU?

Each `std::list` node contains two 8-byte pointers (`prev`, `next`) plus the 8-byte `uint64_t` payload (24 bytes), plus the 16-byte heap allocator metadata header = 40 bytes (only 20% payload efficiency). Furthermore, obtaining the address of node $i+1$ requires waiting for the load of node $i$ to complete (~4–200 cycles per hop).
Concept Check RCU-Safe List Deletion (`list_del_rcu`) staff

In the Linux kernel, `list_del(entry)` overwrites `entry->next = LIST_POISON1` and `entry->prev = LIST_POISON2` after unlinking. However, `list_del_rcu(entry)` leaves `entry->next` intact while poisoning `entry->prev`. Why is leaving `entry->next` unmodified mandatory for Read-Copy-Update (RCU) readers?

An RCU reader holds no locks and might be preempted or delayed while pointing to `entry`. When the writer unlinks `entry` via `WRITE_ONCE(entry->prev->next, entry->next)`, new readers skip `entry`, but an existing reader on `entry` will still read `entry->next` to step forward. Poisoning `entry->next` immediately would cause that reader to fault.

Key Takeaways

Intrusive linked lists (like Linux's struct list_head) embed link pointers directly inside the domain object, eliminating per-node heap allocations and enabling O(1) unlinking from an object pointer.
The container_of macro recovers the enclosing struct pointer from a member pointer in zero memory reads by subtracting compile-time offsetof(Type, member).
Using a circular dummy sentinel node in a doubly linked list—or a Node** pointer-to-pointer in a singly linked list—eliminates all null-check boundary branches on head/tail updates.
Always cache next = curr->next before unlinking, moving, or freeing curr during list traversal (the list_for_each_safe pattern).
