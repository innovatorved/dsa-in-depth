B-Trees & B+ Trees: Page Fanout, Proactive Splitting & Leaf Sibling Chains

7 min read Module 3.2: Self-Balancing, Augmented, Disk-Backed & Persistent Trees Updated Oct 23, 2026
📄 Cheat Sheet
CMU Database Group (Andy Pavlo) CMU 15-445 Database Systems Lecture 7: Trees Indexes (B+ Trees) Watch on YouTube ↗

Andy Pavlo explains why every relational database (PostgreSQL, InnoDB, SQLite) uses B+ Trees instead of original B-Trees, plus latch crabbing and page splits.

Intuition first

Why doesn't PostgreSQL or MySQL InnoDB use a Red-Black Tree or AVL Tree for on-disk indexes? Because on $N = 10^9$ rows, a binary tree has height $\log_2(10^9) \approx 30$. Chasing 30 random pointers across an NVMe SSD ($\approx 50\,\mu\text{s}$ per 4 KB / 16 KB page read) costs $1.5\text{ ms}$ per lookup, and on spinning disks costs $300\text{ ms}$! In 1970, Rudolf Bayer and Edward McCreight solved this by matching the tree node size to the hardware OS/Disk Page Size ($4\text{ KB}$ to $16\text{ KB}$), packing $B \approx 250\text{ to }1000$ keys into a single contiguous node to flatten tree height from $\log_2(10^9) = 30$ down to $\log_{500}(10^9) \le 4$ levels!

Furthermore, virtually every modern database uses Douglas Comer's B+ Tree variant rather than Bayer & McCreight's original B-Tree: by stripping row values/payloads out of internal nodes (leaving internal nodes as pure routing directories of separator keys) and storing all records in a doubly-linked leaf sibling chain, B+ Trees maximize internal node fanout $B$ and turn range queries (WHERE id BETWEEN 100 AND 5000) into linear sequential page scans!

CLRS Minimum Degree $t$ Invariants, Proactive Splitting & B-Tree vs B+ Tree

In CLRS notation, a B-Tree of minimum degree $t \ge 2$ (maximum branching factor $M = 2t$) satisfies:

  1. Every node except the root holds at least $t - 1$ keys ($t$ children); the root holds at least $1$ key ($2$ children) if non-empty.
  2. Every node holds at most $2t - 1$ keys ($2t$ children). A node with $2t - 1$ keys is full.
  3. All leaf nodes reside at the exact same depth $h$, bounded by $h \le \log_t \frac{N + 1}{2}$.

Proactive Top-Down Splitting (Single-Pass Insertion): In an on-disk B-Tree, if we waited until reaching a full leaf to split and propagate median keys back up, we would have to hold exclusive write locks (latches) on the entire root-to-leaf path or re-read ancestor pages from disk. Instead, CLRS splits every full node ($2t - 1$ keys) encountered on the way down into two nodes of $t - 1$ keys each, promoting the median key into the parent (which is guaranteed not to be full because we would have already split it on the step above!). This guarantees single-pass top-down insertion and enables latch crabbing (releasing parent locks as soon as the child is verified safe).

B-Tree Split vs B+ Tree Split: Push-Up vs Copy-Up

When a full node with $2t - 1$ keys splits around its median key $k_{\text{mid}}$:

  • B-Tree Split (Push-Up Everywhere): Because every node stores actual data records, $k_{\text{mid}}$ is moved (pushed) up into the parent and removed from the child level, leaving two children of size $t - 1$.
  • B+ Tree Leaf Split (Copy-Up) vs Internal Split (Push-Up): In a B+ Tree, every key-value record must remain present in the leaf level so sequential scans work! Therefore, when a B+ Tree Leaf splits, the separator key $k_{\text{mid}}$ is copied up to the parent directory node while remaining in the right leaf! When a B+ Tree Internal Routing Node overflows, however, its median routing key is pushed up (not duplicated) just like a standard B-Tree.

Hardware Reality: Why Rust's std::collections::BTreeMap Replaced Red-Black Trees in RAM

B-Trees are not just for disks! Standard C++ std::map allocates every single key in a separate 40-byte Red-Black Tree node on the heap, causing a $60\text{ ns}$ L3/DRAM cache miss on every comparison and wasting $70\%$ of memory on pointers. Rust's standard library (std::collections::BTreeMap) and Google's Abseil absl::btree_map use an in-memory B-Tree with $B = 6$ (up to $2B - 1 = 11$ keys per node). Scanning up to 11 contiguous keys inside a node sits in 1–2 CPU cache lines, runs at L1 speed with hardware prefetching and SIMD, reduces pointer overhead by $85\%$, and beats std::map by $2\times$ to $4\times$ on both lookups and iteration!

Implementation: In-Memory Cache-Aligned B-Tree Node Split (splitChild)

// C++20: Proactive B-Tree Node Split (CLRS Minimum Degree t, Max Keys = 2t - 1)
#include <vector>
#include <algorithm>

template <typename Key, int T = 4> // T=4 => max 7 keys, 8 children per cache-aligned node
struct BTreeNode {
    bool isLeaf = true;
    std::vector<Key> keys;
    std::vector<BTreeNode*> children;

    explicit BTreeNode(bool leaf) : isLeaf(leaf) {
        keys.reserve(2 * T - 1);
        if (!leaf) children.reserve(2 * T);
    }
};

// Splits full child y = parent->children[idx] (which has 2T - 1 keys) into two nodes of T - 1 keys
template <typename Key, int T>
void splitChild(BTreeNode<Key, T>* parent, int idx) {
    BTreeNode<Key, T>* y = parent->children[idx];
    auto* z = new BTreeNode<Key, T>(y->isLeaf);

    Key medianKey = y->keys[T - 1];
    // Move upper T - 1 keys [T .. 2T-2] from y to z
    z->keys.assign(y->keys.begin() + T, y->keys.end());
    y->keys.resize(T - 1);

    // If internal node, move upper T children [T .. 2T-1] from y to z
    if (!y->isLeaf) {
        z->children.assign(y->children.begin() + T, y->children.end());
        y->children.resize(T);
    }

    // Insert medianKey and new right sibling z into parent
    parent->keys.insert(parent->keys.begin() + idx, medianKey);
    parent->children.insert(parent->children.begin() + idx + 1, z);
}

Failure Modes & Adversarial Pitfalls

  • Random-Insertion Page Space Utilisation (~69% = $ln 2$) vs Right-Edge Sequential Inserts: Under random insertions, B+ Tree pages split into two $50\%$ full pages and average $\ln 2 \approx 69\%$ space utilization. If keys are inserted in strictly increasing order (e.g., AUTO_INCREMENT IDs) and pages split $50/50$, the left half is never touched again, wasting $50\%$ of disk space! Production engines (InnoDB, SQLite) detect right-edge monotonic inserts and perform fast $90/10$ or $100/0$ right-leaning splits to achieve $>95\%$ page packing.
  • Write Amplification on Small Random Updates: Updating a single 8-byte integer inside a $16\text{ KB}$ B+ Tree leaf page forces the storage engine to flush the entire $16\text{ KB}$ dirty page (plus WAL record) back to SSD—a $2000\times$ raw write amplification that motivates LSM-Trees!
Check yourself Question 1 of 4
Concept Check B-Tree vs B+ Tree Structural Difference recall

Database storage engines (PostgreSQL, MySQL InnoDB, SQLite table B-trees) use **B+ Trees** rather than classic Bayer-McCreight **B-Trees**. What are the two defining structural differences of a B+ Tree?

By stripping bulky row values or tuple pointers out of internal pages, an internal 16 KB B+ tree page can pack hundreds of separator keys (branching factor B ~ 500–1000), keeping a 1-billion-row table at height 3–4. Furthermore, linking all leaf pages horizontally allows a range query `WHERE k BETWEEN a AND b` to perform one root-to-leaf descent followed by a sequential scan across sibling leaf pages.
Concept Check Page Capacity & Tree Height Calculation apply

A database uses $16\text{ KB}$ ($16{,}384$-byte) pages. Each internal B+ tree page has a $64$-byte header, stores $8$-byte `int64` separator keys and $8$-byte child page IDs. Leaf pages hold up to $64$ full row records each. Assuming pages are at least $70\%$ full on average, how many disk page reads are needed to fetch a record in a $100{,}000{,}000$-row ($10^8$) table if the top 2 levels of the B+ tree are pinned in the RAM buffer pool?

An internal page holds (16384 - 64) / (8 + 8) = 1020 child pointers at 100% capacity, or ~714 at 70% occupancy. Leaf pages at 70% occupancy hold ~45 rows. Thus 1 root * 714 L1 pages * 714 L2 pages = 509,796 L2 pages, pointing to 509,796 * 714 = 364M leaf pages (> 1.6 * 10^{10} rows). For 10^8 rows (~2.2M leaf pages), a 4-level B+ tree (Root -> L1 -> L2 -> Leaf) easily suffices. With Root and L1 cached in RAM, only L2 and the target Leaf require disk reads (2 I/Os).
Concept Check Proactive Top-Down Splitting in B-Trees apply

In CLRS proactive (top-down) B-tree insertion with minimum degree $t$ (where each node holds between $t-1$ and $2t-1$ keys), what does the algorithm do whenever it encounters a full node with $2t-1$ keys on its way down from the root?

If we wait until reaching a full leaf to split, the median key promoted to the parent might overflow the parent, cascading splits all the way to the root and requiring us to hold exclusive locks on the entire root-to-leaf path. By splitting any full (2t - 1 key) node into two (t - 1 key) nodes as we descend, the parent is guaranteed to have spare capacity (< 2t - 1 keys), allowing single-pass top-down insertion with lock crabbing.
Concept Check Lehman-Yao B-Link Trees and High-Keys for Lock-Free/Latch-Free Reads staff

In PostgreSQL's `nbtree` implementation (based on Lehman & Yao's B-link tree), what could happen if a reader thread reads a parent page's child pointer $P$, and before the reader latches child page $P$, a concurrent writer splits $P$ into $P$ and $P_{\text{right}}$?

Lehman and Yao's B-link tree adds a `high_key` and a `right_link` to every internal and leaf page, and ensures a page split writes the new right sibling `P_right` and updates `P`'s `high_key` and `right_link` BEFORE inserting the separator into the parent. If a reader lands on `P` after `P` was split and the target key migrated to `P_right`, the reader sees `search_key > P.high_key` and follows `P.right_link` rightwards without ever needing to hold simultaneous latches on parent and child!

Key Takeaways

B-Trees match node sizes to hardware storage units (4KB–16KB disk pages or 64B–256B CPU cache lines), increasing fanout B to 250–1000 so 10^9 keys require only 3–4 tree levels.
Proactive top-down splitting splits every full (2t - 1)-key node encountered on the way down, guaranteeing the parent always has room for a promoted median key in a single pass.
B+ Trees store row payloads exclusively in leaf pages and link leaves into a doubly-linked sibling chain, maximizing internal routing fanout and turning range queries into sequential scans.
When a B+ Tree leaf splits, the separator key is COPIED up to the parent (remaining in the right leaf); when an internal directory node splits, the median key is PUSHED up.
