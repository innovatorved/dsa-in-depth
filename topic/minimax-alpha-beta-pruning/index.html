Intuition first

In a zero-sum game, you don't need to find out whether an opponent's reply is merely bad for you or catastrophically bad for you—as soon as the opponent finds one reply worse than a safe option you already have in another branch, you can immediately abandon the entire move. With good move ordering, Alpha-Beta pruning cuts the effective branching factor from b to sqrt(b), letting your engine see twice as many moves ahead in the same time.

1. Minimax, Negamax & The Alpha-Beta Pruning Window

In a two-player deterministic zero-sum game of perfect information (Chess, Go, Checkers, Connect Four), the Minimax value of state $s$ is the best score the active player can guarantee against a perfect opponent. Rather than writing separate max_value() and min_value() functions, production engines use Negamax, relying on the zero-sum symmetry $\max(a, b) = -\min(-a, -b)$ and evaluating every board strictly from the side-to-move's perspective.

Core Invariant — The $[\alpha, \beta]$ Search Window in Negamax

At any node in Negamax:

  • $\alpha$ (Lower Bound): The minimum score the current side-to-move is already guaranteed by a previously explored path.
  • $\beta$ (Upper Bound): The maximum score the opponent will allow us to achieve here (because if we can achieve $\ge \beta$, the opponent will deviate at an ancestor node where they already have a better alternative $-\beta$).

When recursing to a child state $s'$, the roles swap and signs negate: the child is searched with window $[\alpha', \beta'] = [-\beta, -\alpha]$. As soon as any move achieves $\text{score} \ge \beta$ ($alpha \ge \beta$), a Beta-Cutoff (Fail-High) occurs and all remaining sibling moves are pruned.

2. The $\Theta(b^{d/2})$ Theorem, Iterative Deepening & Zobrist Hashing

How much does Alpha-Beta prune? If moves are searched in worst-first order, Alpha-Beta prunes nothing and visits all $b^d$ leaves. If moves are searched in best-first order (the best move at each node is tried first), Knuth and Moore (1975) proved that Alpha-Beta visits exactly:

$$N_{\text{best}} = b^{\lceil d/2 \rceil} + b^{\lfloor d/2 \rfloor} - 1 = \Theta(b^{d/2})$$

This reduces the effective branching factor from $b$ to $\sqrt{b}$ (e.g., in Chess from $b \approx 35$ to $\sqrt{35} \approx 6$), literally doubling the reachable search depth within a fixed time budget! To achieve near-perfect move ordering and avoid re-searching identical positions reached via different move sequences (transpositions):

  • Zobrist Hashing (1970): Pre-generate a table of random 64-bit integers $Z[\text{piece}][\text{square}]$. The hash of a board is the XOR of $Z[p][sq]$ for all pieces on the board. Making or unmaking a move updates the 64-bit hash in $O(1)$ time via 2 or 3 XORs!
  • Transposition Table (TT) Node Types: A cached depth-$d$ search over window $[\alpha, \beta]$ stores one of three bound flags:
    1. EXACT (PV-Node, $\alpha < v < \beta$): True minimax value is $v$.
    2. LOWER_BOUND (Cut-Node / Beta-Cutoff, $v \ge \beta$): True value is $\ge v$.
    3. UPPER_BOUND (All-Node / Fail-Low, $v \le \alpha$): True value is $\le v$.
  • Iterative Deepening ($d = 1, 2, \dots, D$): Searching depths $1 \dots D-1$ adds only $\frac{1}{\sqrt{b} - 1}$ overhead, while populating the Transposition Table with the best move (TT-move) at every node—guaranteeing near-optimal move ordering for depth $D$!

Hardware Reality — Lockless Power-of-2 Transposition Tables & Cache-Line Alignment

Using std::unordered_map<uint64_t, TTEntry> in a game engine destroys performance due to heap node allocations and pointer chasing. Production engines (like Stockfish) allocate a single flat power-of-2 array of 16-byte or 64-byte cache-line-aligned TTEntry structs indexed by zobrist_hash & (table_size - 1), issuing __builtin_prefetch(&tt[hash & mask]) as soon as a move is made so the cache line arrives from DRAM before evaluation begins.

4. Reference C++20 Implementation

#include <algorithm>
#include <cstdint>
#include <vector>

enum class BoundFlag : std::uint8_t { NONE = 0, EXACT = 1, LOWER = 2, UPPER = 3 };

struct TTEntry {
    std::uint64_t key = 0;
    int value = 0;
    int depth = -1;
    int best_move = -1;
    BoundFlag flag = BoundFlag::NONE;
};

// Generic Negamax with Alpha-Beta Pruning and Zobrist Transposition Table
template <typename GameState>
class AlphaBetaEngine {
    std::vector<TTEntry> tt;
    std::size_t mask;
    static constexpr int INF = 1'000'000'000;

public:
    explicit AlphaBetaEngine(std::size_t power_of_two_entries = (1ULL << 20))
        : tt(power_of_two_entries), mask(power_of_two_entries - 1) {}

    int negamax(GameState& state, int depth, int alpha, int beta) {
        const int alpha_orig = alpha;
        const std::uint64_t h = state.zobrist_hash();
        TTEntry& entry = tt[h & mask];

        // 1. Transposition Table Lookup
        int tt_move = -1;
        if (entry.flag != BoundFlag::NONE && entry.key == h) {
            tt_move = entry.best_move;
            if (entry.depth >= depth) {
                if (entry.flag == BoundFlag::EXACT) return entry.value;
                if (entry.flag == BoundFlag::LOWER) alpha = std::max(alpha, entry.value);
                else if (entry.flag == BoundFlag::UPPER) beta = std::min(beta, entry.value);
                if (alpha >= beta) return entry.value; // TT Cutoff!
            }
        }

        // 2. Base Case: Terminal State or Horizon Depth
        if (depth == 0 || state.is_terminal()) {
            return state.evaluate_for_side_to_move();
        }

        // 3. Move Generation + Move Ordering (Prioritize TT Best Move first!)
        std::vector<int> moves = state.generate_moves();
        if (tt_move != -1) {
            auto it = std::find(moves.begin(), moves.end(), tt_move);
            if (it != moves.end()) std::iter_swap(moves.begin(), it);
        }

        int best_val = -INF;
        int best_move = moves.empty() ? -1 : moves[0];

        for (int m : moves) {
            state.make_move(m);
            int score = -negamax(state, depth - 1, -beta, -alpha);
            state.undo_move(m);

            if (score > best_val) {
                best_val = score;
                best_move = m;
            }
            if (score > alpha) {
                alpha = score;
            }
            if (alpha >= beta) {
                break; // Beta-Cutoff (Fail-High)
            }
        }

        // 4. Transposition Table Store with Correct Bound Classification
        entry.key = h;
        entry.value = best_val;
        entry.depth = depth;
        entry.best_move = best_move;
        if (best_val <= alpha_orig) {
            entry.flag = BoundFlag::UPPER;
        } else if (best_val >= beta) {
            entry.flag = BoundFlag::LOWER;
        } else {
            entry.flag = BoundFlag::EXACT;
        }
        return best_val;
    }
};

Production Pitfall — Caching Cut-Nodes as Exact Values & -INT_MIN Overflow

Two bugs silently break Negamax engines: First, when a node fails high ($ ext{best_val} ge eta$) or fails low ($ ext{best_val} le alpha_{ ext{orig}}$), the search did not compute the true minimax value—it only proved an inequality! Storing it as EXACT in the Transposition Table will poison future searches that probe the same position with a wider $[alpha, eta]$ window. Second, never set INF = INT_MAX and pass -INT_MIN; in two's complement signed 32-bit arithmetic, -INT_MIN overflows (UB) back to INT_MIN. Always use a safe sentinel like 1'000'000'000.

Concept Check Optimal Move Ordering in Alpha-Beta Pruning recall

For a uniform game tree of branching factor $b$ and depth $d$, how many leaf nodes does Alpha-Beta pruning evaluate when moves are ordered optimally (best move searched first at every node)?

By Knuth and Moore's theorem (1975), perfect move ordering reduces the number of evaluated leaves from $b^d$ to $b^{\lceil d/2 \rceil} + b^{\lfloor d/2 \rfloor} - 1 = \Theta(b^{d/2})$, reducing the effective branching factor from $b$ to $\sqrt{b}$.
Napkin Math · Capacity Alpha-Beta Cutoff Leaf Count apply

Consider a 2-ply game tree with a MAX root $R$ and two MIN children $M_1, M_2$, each having 3 leaf children. The leaves of $M_1$ (left-to-right) have values $[5, 8, 6]$, and the leaves of $M_2$ (left-to-right) have values $[3, 9, 2]$. How many total leaf nodes (out of 6) are evaluated by left-to-right Alpha-Beta search?

±0% accepted
Under $M_1$, all 3 leaves $[5, 8, 6]$ are evaluated, giving $M_1 = \min(5, 8, 6) = 5$ and updating the root's lower bound to $\alpha = 5$. Next, under $M_2$ (with window $\alpha = 5, \beta = +\infty$), the first leaf has value $3$. Since $M_2$ is a MIN node, its value is now at most $3 \le \alpha = 5$, triggering an immediate cutoff! The remaining 2 leaves $[9, 2]$ are pruned, so $3 + 1 = 4$ leaves are evaluated.
Concept Check Zobrist Hash Incremental Update apply

In a chess engine using Zobrist hashing (`Z[piece][square]`), suppose a White Knight (`WN`) moves from square `f3` to capture a Black Pawn (`BP`) on square `d4` (ignoring castling/en-passant/side-to-move flags). How is the board hash `h` updated in $O(1)$ time?

Because XOR is its own inverse ($x \oplus x = 0$), XORing `Z[WN][f3]` removes the White Knight from `f3`, XORing `Z[BP][d4]` removes the captured Black Pawn from `d4`, and XORing `Z[WN][d4]` places the White Knight on `d4`.

During a Negamax search of state $s$ with initial window $[\alpha_{\text{orig}}, \beta]$, suppose a move produces score $v \ge \beta$, causing an immediate Beta-Cutoff (`break`). Why must the Transposition Table store this entry with `BoundFlag::LOWER` instead of `BoundFlag::EXACT`?

When a Beta-Cutoff occurs at move $m$ with score $v \ge \beta$, remaining legal moves at state $s$ are skipped. One of those skipped moves might have achieved $v' > v$. Therefore, $v$ is a proven **lower bound** ($\text{true\_value}(s) \ge v$), not necessarily the exact minimax value.

Key Takeaways

Negamax unifies Min and Max levels via max(a, b) = -min(-a, -b), passing [-beta, -alpha] to child states.
With optimal move ordering, Alpha-Beta pruning reduces leaf evaluations from O(b^d) to O(b^(d/2)), doubling reachable search depth.
Zobrist hashing assigns random 64-bit integers to (piece, square) pairs so board hashes update incrementally in O(1) XOR operations per move.
Transposition tables must distinguish EXACT, LOWER_BOUND (beta-cutoff), and UPPER_BOUND (fail-low) entries relative to the original search window.
