Augmenting BSTs: Order-Statistic Trees (select/rank) & Interval Trees

7 min read Module 3.2: Self-Balancing, Augmented, Disk-Backed & Persistent Trees Updated Oct 23, 2026
📄 Cheat Sheet
MIT OpenCourseWare MIT 6.006 Lecture 7: Augmenting Data Structures (Order Statistics & Interval Trees) Watch on YouTube ↗

Covers the CLRS Augmentation Theorem, Order-Statistic select/rank algorithms, and Interval Tree max-endpoint invariant proof.

Intuition first

A standard balanced BST only answers predecessor/successor and key membership queries in $O(\log N)$ time; it cannot directly answer positional array queries like "what is the $k$-th smallest element?" (select(k)) or "how many elements are strictly less than $x$?" (rank(x)), nor geometric overlap queries like "which scheduled reservation overlaps $[lo, hi]$?". Instead of inventing a brand-new data structure from scratch for every domain, we augment an existing balanced BST (AVL, Red-Black, or Treap) by storing extra cached summary fields inside each node.

By the CLRS Augmentation Theorem (Theorem 14.1), any node attribute $f(u)$ that can be computed in $O(1)$ time solely from $u$'s own key and the attributes of $u$'s immediate children—$f(u) = g(u.\text{key}, f(u.\text{left}), f(u.\text{right}))$—can be maintained across all BST insertions, deletions, and rotations in $O(\log N)$ time without increasing asymptotic complexity!

The CLRS Augmentation Theorem & Two Canonical Augmented Trees

Why do rotations preserve local subtree summaries in $O(1)$ time? Because a rotation (rotateLeft or rotateRight) on edge $(x, y)$ only changes the descendant sets of two nodes: $x$ and $y$! The entire subtree rooted at the new top node contains the exact same set of nodes as before the rotation, so no ancestor above the rotated pair needs its associative summary recomputed from scratch (though ancestor updates along the $O(\log N)$ insertion/deletion path take $O(\log N)$ total time anyway).

1. Order-Statistic Tree (size[u] Augmentation)

Augment each node $u$ with its subtree size $\text{size}(u) = 1 + \text{size}(u.\text{left}) + \text{size}(u.\text{right})$ (where $\text{size}(\text{null}) = 0$). Then:

  • select(u, k) (0-indexed $k$-th smallest key): Let $L = \text{size}(u.\text{left})$ be the number of nodes in $u$'s left subtree. If $k == L$, return $u$; if $k < L$, recurse into select(u.left, k); if $k > L$, subtract the $L + 1$ skipped elements and recurse into select(u.right, k - L - 1)!
  • rank(root, key) (count of keys $< \text{key}$): Walk down from the root; every time we branch right (because $u.\text{key} < \text{key}$), add $\text{size}(u.\text{left}) + 1$ to our running accumulator.

2. Interval Tree (maxEnd[u] Augmentation for 1D Overlap Search)

Suppose we store closed intervals $I_i = [lo_i, hi_i]$ ordered primarily by their low endpoint $lo_i$ as the BST key, and augment each node $u$ with the maximum high endpoint anywhere in $u$'s subtree:

$$\text{maxEnd}(u) = \max\big(u.hi, \; \text{maxEnd}(u.\text{left}), \; \text{maxEnd}(u.\text{right})\big)$$

To find any interval in the tree that overlaps query $Q = [q_{lo}, q_{hi}]$ (recall two closed intervals overlap iff $u.lo \le q_{hi}$ AND $q_{lo} \le u.hi$), we inspect a **single root-to-leaf path** in $O(\log N)$ time:

  1. If $u$ overlaps $Q$, return $u$.
  2. If $u.\text{left} \ne \text{null}$ and $\text{maxEnd}(u.\text{left}) \ge q_{lo}$, go left (u = u.left).
  3. Otherwise, go right (u = u.right).

Correctness Proof: Why Interval Tree Search Never Needs to Backtrack When Going Left!

Students always ask: "In Step 2, if $\text{maxEnd}(u.\text{left}) \ge q_{lo}$ and we go left, what if the interval in $u.\text{left}$ that achieved $\text{maxEnd} \ge q_{lo}$ has its low endpoint $> q_{hi}$, so the left subtree has NO overlap while the right subtree DOES have an overlap?"

Proof that this is impossible: Let $I^* = [lo^*, hi^*] \in u.\text{left}$ be the interval in $u$'s left subtree that achieves $hi^* = \text{maxEnd}(u.\text{left}) \ge q_{lo}$.

  • Case A: If $lo^* \le q_{hi}$, then since we already know $hi^* \ge q_{lo}$, $I^*$ itself overlaps $Q = [q_{lo}, q_{hi}]$! So an overlapping interval genuinely exists in $u.\text{left}$.
  • Case B: Suppose $lo^* > q_{hi}$. Because $I^*$ lies in the left subtree of $u$ and the BST is ordered by low endpoints, every interval $J = [lo_J, hi_J]$ in $u$'s right subtree satisfies: $$lo_J \ge u.lo \ge lo^* > q_{hi}!$$ Thus no interval in $u.\text{right}$ can possibly overlap $Q$ either! Going left when $\text{maxEnd}(u.\text{left}) \ge q_{lo}$ is 100% safe and never misses a valid match in $u.\text{right}$.

Hardware Reality: Linux Kernel VMAs & GCC Policy-Based Data Structures

Where do Augmented BSTs appear in production? First, the Linux kernel's Virtual Memory Area manager (mm/mmap.c) uses an augmented Red-Black Interval Tree (rb_subtree_gap) to locate free virtual address holes for mmap() in $O(\log N)$ time. Second, in C++ competitive and systems programming, GNU libstdc++ provides __gnu_pbds::tree with tree_order_statistics_node_update, giving a drop-in Red-Black Order-Statistic Tree supporting find_by_order(k) (select) and order_of_key(x) (rank) in $O(\log N)$ time.

Implementation: Interval Tree Overlap Search & Order-Statistic Select/Rank

// C++20: Augmented BST Primitives — Interval Overlap Search + Order-Statistic Select & Rank
#include <algorithm>
#include <cstdint>

struct AugmentedNode {
    int64_t lo, hi;      // Interval [lo, hi]; 'lo' acts as the primary BST key
    int64_t maxEnd;      // Max 'hi' in subtree
    int32_t sz = 1;      // Subtree node count for Order-Statistic rank/select
    AugmentedNode *left = nullptr, *right = nullptr;

    AugmentedNode(int64_t l, int64_t h) : lo(l), hi(h), maxEnd(h) {}
};

// O(1) Local Pull called after every child modification or rotation
inline void pullAugmented(AugmentedNode* u) noexcept {
    if (!u) return;
    u->sz = 1 + (u->left ? u->left->sz : 0) + (u->right ? u->right->sz : 0);
    int64_t m = u->hi;
    if (u->left)  m = std::max(m, u->left->maxEnd);
    if (u->right) m = std::max(m, u->right->maxEnd);
    u->maxEnd = m;
}

// 1. O(log N) Interval Overlap Search (Single root-to-leaf walk, zero backtracking!)
const AugmentedNode* findOverlappingInterval(const AugmentedNode* u, int64_t qLo, int64_t qHi) noexcept {
    while (u != nullptr) {
        if (u->lo <= qHi && qLo <= u->hi) return u; // Overlap found!
        if (u->left != nullptr && u->left->maxEnd >= qLo) {
            u = u->left;
        } else {
            u = u->right;
        }
    }
    return nullptr;
}

// 2. O(log N) Order-Statistic Select (0-indexed k-th smallest by 'lo')
const AugmentedNode* selectKth(const AugmentedNode* u, int32_t k) noexcept {
    while (u != nullptr) {
        int32_t leftSz = u->left ? u->left->sz : 0;
        if (k == leftSz) return u;
        if (k < leftSz) {
            u = u->left;
        } else {
            k -= (leftSz + 1);
            u = u->right;
        }
    }
    return nullptr;
}

Failure Modes & Adversarial Pitfalls

  • Augmenting with Global Rank Instead of Local Subtree Size Breaks $O(\log N)$ Insertion: If you store each node's global sorted index globalRank[u] inside the node, inserting a new minimum element increments the global rank of all $N$ nodes, forcing $\Theta(N)$ updates! By storing only subtree-local size[u], inserting a node only increments size on its $O(\log N)$ ancestors.
  • Forgetting to Call pullAugmented Inside Rotations: Any rotation rotateLeft(x) or rotateRight(x) changes the children of both x and y. Omitting pullAugmented(x); pullAugmented(y); inside the rotation helper leaves stale size and maxEnd values that cause silent out-of-bounds select or missed interval overlaps.

Concept Check The Augmentation Theorem for Balanced BSTs recall

According to the CLRS Augmentation Theorem, when can an auxiliary field $f(x)$ stored at every node $x$ of a balanced BST be maintained in $O(\log N)$ time during insertions, deletions, and rotations without changing the asymptotic complexity?

When a rotation occurs between parent x and child y, only the subtrees rooted at x and y change their immediate child pointers; all subtrees below them remain intact, and the combined set of nodes under the rotated pair is unchanged. If f(u) depends only on u.key, f(u.left), and f(u.right), then recomputing f(x) and f(y) after a rotation takes O(1) time, and propagating updates up to the root takes O(log N) time.
Concept Check Order-Statistic Tree `rank(key)` Calculation apply

In an Order-Statistic Tree where each node stores `u.size = 1 + size(u.left) + size(u.right)`, you are searching for the 0-based rank (number of keys strictly less than `q`) of query key `q`.

If q <= u.key, neither u nor any node in u.right is strictly less than q, so all keys < q within u's subtree must lie inside u.left; we descend left with r unchanged. If q > u.key, then u itself AND every node in u.left are strictly less than q, so we add `size(u.left) + 1` to r and descend into u.right to count any remaining keys < q.
Concept Check Interval Tree Single-Path Overlap Search Proof apply

In CLRS Interval Trees, each node stores an interval $[low, high]$, is keyed by $low$, and maintains $max = \max(high, left.max, right.max)$. During `overlapSearch([ql, qr])` at node $u$, if $u$ does not overlap $[ql, qr]$, the algorithm checks `if (u.left != null && u.left.max >= ql)` and goes left ONLY, never backtracking to the right subtree.

Let [l*, r*] be the interval in u.left that achieves r* = u.left.max >= ql. Either [l*, r*] overlaps [ql, qr] (in which case moving left finds an overlap), OR [l*, r*] does not overlap [ql, qr]. Since r* >= ql is already true, the only way [l*, r*] fails to overlap [ql, qr] is if l* > qr. By the BST property on `low` endpoints, every interval in u.right has low >= u.low >= l* > qr, so it is impossible for ANY interval in u.right to overlap [ql, qr]!
Concept Check Why Storing Explicit `rank` Breaks the Augmentation Theorem staff

A developer proposes storing `u.globalRank` (the node's index in the sorted order of the entire tree) directly inside every BST node instead of `u.size` (the subtree node count) so that `rank(u)` takes $O(1)$ pointer lookup.

The Augmentation Theorem requires that a node's augmented attribute be a function solely of its own subtree (`u`, `u.left`, `u.right`). `u.size` satisfies this local subtree property; `u.globalRank` depends on the number of nodes to the left of `u` across the entire tree. Inserting a single element smaller than the minimum shifts the global rank of all N nodes, forcing O(N) updates.

Key Takeaways

By the CLRS Augmentation Theorem, any subtree property f(u) = g(u.val, f(u.left), f(u.right)) computable in O(1) from children can be maintained across balanced BST updates and rotations in O(log N) time.
Order-Statistic Trees augment nodes with subtree size sz(u) = 1 + sz(u.left) + sz(u.right) (never global rank!) to answer select(k) and rank(key) in O(log N) time.
Interval Trees order intervals by low endpoint lo and augment each node with maxEnd(u) = max(u.hi, maxEnd(L), maxEnd(R)).
Searching for any overlapping interval follows a single O(log N) path: if maxEnd(u.left) >= q_lo, going left is guaranteed safe because if the left witness lo* > q_hi, then every interval in u.right has lo >= lo* > q_hi and cannot overlap either.
