Intuition first

Building a production-grade $O(1)$ LFU Cache requires orchestrating three invariants simultaneously without a single memory leak or dangling iterator: (1) a key lookup table key -> Node, (2) per-frequency circular doubly linked lists freq -> List that preserve LRU tie-breaking within each frequency tier, and (3) a deterministic min_freq cursor that tracks the lowest populated frequency bucket in $O(1)$ time.

End-to-End State Machine of the $O(1)$ LFU Engine

Let us trace every edge case required to implement a zero-allocation, bug-free $O(1)$ LFU Cache of capacity $C$. Every cached item is represented by a Node containing {key, value, freq, prev, next}. We maintain:

  • key_table: Maps key -> Node* (or arena slot index).
  • freq_table: Maps freq -> DoublyLinkedList, where each list orders nodes of that exact frequency from Most Recently Used (front) to Least Recently Used (back).
  • min_freq: An integer tracking the smallest frequency $f \ge 1$ such that freq_table[f] is non-empty.
Verification Checklist: The 4 Invariant Transitions of O(1) LFU
  1. Transition 1 — Cache Hit on get(key): Find node $u$ with frequency $f = u.\text{freq}$. Unlink $u$ from freq_table[f]. If freq_table[f].empty() and $f == \text{min\_freq}$, set $\text{min\_freq} = f + 1$. Set $u.\text{freq} = f + 1$ and push $u$ to the MRU front of freq_table[f + 1]. Return $u.\text{value}$.
  2. Transition 2 — Cache Hit on put(key, new_val): Overwrite $u.\text{value} = \text{new\_val}$, and execute the exact same frequency promotion logic as Transition 1!
  3. Transition 3 — Cache Miss on put(key, val) when Full (size == capacity): Look up bucket freq_table[min_freq]. Pop its LRU tail node $v$, and erase $v.\text{key}$ from key_table. (Note: we do NOT need to update min_freq based on $v$'s removal because we are about to reset min_freq = 1 in Transition 4!)
  4. Transition 4 — Inserting the New Node on put(key, val): Initialize node $w$ with $\text{freq} = 1$, push $w$ to the MRU front of freq_table[1], insert key_table[key] = w, and unconditionally set min_freq = 1.

Hardware Reality: Eliminating Empty Bucket Bloat & std::list Allocator Thrashing

A textbook C++ LFU implementation using std::unordered_map<int, std::list<Node>> freq_table suffers from two performance hazards in long-running services:

  1. Per-Promotion Heap Allocations: Calling freq_table[f].erase(it) and freq_table[f+1].push_front(...) deallocates a heap node and allocates a brand-new heap node on every single cache hit! Using std::list::splice (or intrusive doubly linked list nodes) moves the existing node between frequency buckets by rewiring 4 pointers with zero heap allocations.
  2. Unbounded Empty Frequency Buckets: If a hot item is accessed $10^7$ times, a naive freq_table creates $10^7$ empty std::list entries for frequencies $1, 2, \dots, 10^7 - 1$, exhausting gigabytes of RAM! In production, either erase empty buckets from freq_table when their size hits 0, or store frequency buckets as an intrusive doubly linked list of active frequency headers.

Production Implementation: Zero-Allocation Intrusive O(1) LFU Cache Engine

C++20
#include <cstdint>
#include <unordered_map>
#include <vector>

class LFUCache {
  struct Node {
    int key = 0;
    int value = 0;
    int freq = 1;
    int prev = -1;
    int next = -1;
  };

  struct FreqList {
    int head = -1; // MRU front
    int tail = -1; // LRU back
    int count = 0;
  };

  int capacity_;
  int size_ = 0;
  int min_freq_ = 0;
  std::vector<Node> pool_;
  std::vector<int> free_slots_;
  std::unordered_map<int, int> key_to_slot_;
  std::unordered_map<int, FreqList> freq_lists_;

  void remove_from_list(int slot, int freq) {
    auto it = freq_lists_.find(freq);
    FreqList& list = it->second;
    const int p = pool_[slot].prev;
    const int n = pool_[slot].next;

    if (p != -1) pool_[p].next = n;
    else list.head = n;

    if (n != -1) pool_[n].prev = p;
    else list.tail = p;

    pool_[slot].prev = pool_[slot].next = -1;
    if (--list.count == 0) {
      freq_lists_.erase(it); // Prevent unbounded empty bucket memory leak!
      if (min_freq_ == freq) {
        ++min_freq_;
      }
    }
  }

  void push_front_list(int slot, int freq) {
    FreqList& list = freq_lists_[freq];
    pool_[slot].prev = -1;
    pool_[slot].next = list.head;
    if (list.head != -1) pool_[list.head].prev = slot;
    else list.tail = slot;
    list.head = slot;
    ++list.count;
  }

  void touch(int slot) {
    const int f = pool_[slot].freq;
    remove_from_list(slot, f);
    pool_[slot].freq = f + 1;
    push_front_list(slot, f + 1);
  }

public:
  explicit LFUCache(int capacity) : capacity_(capacity), pool_(capacity > 0 ? capacity : 0) {
    for (int i = capacity - 1; i >= 0; --i) {
      free_slots_.push_back(i);
    }
  }

  int get(int key) {
    auto it = key_to_slot_.find(key);
    if (it == key_to_slot_.end()) return -1;
    const int slot = it->second;
    touch(slot);
    return pool_[slot].value;
  }

  void put(int key, int value) {
    if (capacity_ <= 0) return;

    auto it = key_to_slot_.find(key);
    if (it != key_to_slot_.end()) {
      const int slot = it->second;
      pool_[slot].value = value;
      touch(slot);
      return;
    }

    int slot = -1;
    if (size_ == capacity_) {
      // Evict LRU tail of min_freq_ BEFORE resetting min_freq_ = 1!
      const int victim = freq_lists_[min_freq_].tail;
      remove_from_list(victim, min_freq_);
      key_to_slot_.erase(pool_[victim].key);
      slot = victim; // Reuse evicted slot in place!
    } else {
      slot = free_slots_.back();
      free_slots_.pop_back();
      ++size_;
    }

    pool_[slot].key = key;
    pool_[slot].value = value;
    pool_[slot].freq = 1;
    push_front_list(slot, 1);
    key_to_slot_[key] = slot;
    min_freq_ = 1;
  }
};
Production Pitfall: Evicting After Inserting & Leaking Empty Frequency Buckets

When implementing LFUCache::put on a cache miss when size == capacity, you must always evict the victim from freq_lists_[min_freq_] BEFORE inserting the new key and resetting min_freq_ = 1. If you insert the new key first (or set min_freq_ = 1 first), and the old min_freq_ was $> 1$, then evicting from min_freq_ == 1 will immediately evict the brand-new item you just inserted! Additionally, always erase a frequency bucket from freq_lists_ when its count drops to 0 so long-running caches do not leak millones of empty hash entries as item frequencies climb.

Check yourself Question 1 of 4
Concept Check Zero-Allocation Slab Handle vs Heap Pointer recall

In our production `FlatO1LfuCache` implementation, all cache nodes live in a pre-allocated contiguous vector `nodes[0..capacity-1]`, and `prev` / `next` / `freeHead` are stored as `int32_t` array indices (`NULL_IDX = -1`) instead of 64-bit `Node*` pointers. Which two major production hazards does this eliminate?

Using `int32_t` slab indices cuts the link metadata from 16 bytes (`prev*`, `next*`) to 8 bytes (`prev`, `next`), keeps all nodes tightly packed in contiguous virtual memory pages, and completely eliminates heap allocator overhead during high-churn eviction loops.
Concept Check Eviction Ordering and Bucket Cleanup in `put(key, val)` apply

Suppose an LFU cache has `capacity = 2`. We call `put(1, 10)`, `put(2, 20)`, `get(1)` (so key 1 has `freq = 2`, key 2 has `freq = 1`, and `minFreq = 1`), and then `put(3, 30)`. Trace the exact state transitions during `put(3, 30)`.

Eviction MUST happen *before* inserting the new key: otherwise, setting `minFreq = 1` and inserting the new key into bucket 1 before evicting could either exceed the fixed slab capacity or corrupt the victim selection in bucket 1. Furthermore, recycling the evicted victim's slab slot directly for the incoming key achieves zero allocation.
Concept Check Memory Leak Hazard in Frequency Bucket Map apply

Consider an LFU cache where a single hot key is accessed $10^7$ times (`get(hotKey)` in a tight loop). On each hit, `hotKey` moves from `freqBuckets[f]` to `freqBuckets[f + 1]`. What happens if `unlinkFromBucket(f, idx)` does NOT call `freqBuckets.erase(f)` when bucket `f` becomes empty?

The number of *non-empty* frequency buckets can never exceed the cache capacity $C$ (since each of the $C$ items belongs to exactly one bucket). However, the maximum frequency value $f$ grows unboundedly with the number of hits. Deleting a bucket entry as soon as its head becomes `NULL_IDX` strictly bounds `freqBuckets.size() <= C`.
Concept Check Why S3-FIFO (SOSP '23) Replaces Doubly Linked Lists with Three FIFO Queues staff

Recent systems research (Yang et al., SOSP 2023, *'FIFO queues are all you need for cache eviction'*) introduced **S3-FIFO**, which uses a small FIFO queue (`S`, 10% capacity), a main FIFO queue (`M`, 90% capacity), and a ghost FIFO queue (`G`, storing only evicted key hashes). Why does S3-FIFO achieve both lower miss ratios than LRU/W-TinyLFU on production traces AND up to $6\times$ higher throughput on 16+ CPU cores?

In LRU, every read hit requires unlinking and relinking a doubly linked list node under a lock or CAS loop. In S3-FIFO, queues are pure FIFO: nodes only move during *insert* or *eviction* (cache misses). Read hits merely increment a saturating 2-bit counter inside the object header, making cache hits completely lock-free and scalable across cores while filtering scan pollution via the 10% probationary queue `S`.

Key Takeaways

In an O(1) LFU cache, updating an existing key via put(key, val) must increment its frequency and promote it just like get(key).
When the cache is full on a miss, always evict the LRU tail of freq_lists[min_freq] BEFORE inserting the new key at freq = 1 and setting min_freq = 1.
Reusing pre-allocated node slots (or using std::list::splice) moves nodes across frequency tiers in O(1) time with zero heap allocations.
Erasing empty frequency buckets from freq_lists when their count reaches 0 prevents unbounded memory growth when items are accessed millions of times.
