Explains why std::lower_bound is bottlenecked by cache misses and associative cache-set aliasing on power-of-2 arrays, and how Eytzinger layout with software prefetching achieves a 3x-4x speedup.

Intuition first

Standard binary search (std::lower_bound) on a sorted array jumps across memory by N/2, N/4, N/8... incurring a fresh cache miss on almost every step until the final 3 steps, AND suffering associative cache-set thrashing when N is a power of two. Storing the array in 1-indexed Breadth-First Search (Eytzinger / Binary Heap) order packs the top 4 levels of the decision tree into a single 64-byte cache line and lets us prefetch 4 levels ahead via __builtin_prefetch(&b[k * 16])!

Why std::lower_bound Is Slow on Modern Hardware

Given a static sorted table of N=220N = 2^{20}N=220 (1,048,5761{,}048{,}5761,048,576) 32-bit integers (4 MB4\text{ MB}4 MB), how fast is std::lower_bound? Textbook complexity says 202020 comparisons. Hardware reality says ~16 sequential DRAM/L3 memory stalls for three architectural reasons analyzed by Paul-Virak Khuong and Pat Morin (2017):

  1. Zero Spatial Locality in the Top log⁡2N−4\log_2 N - 4log2​N−4 Levels: A 646464-byte CPU cache line holds sixteen 32-bit integers. Standard sorted order packs adjacent ranks (A[i],A[i+1],…,A[i+15]A[i], A[i+1], \dots, A[i+15]A[i],A[i+1],…,A[i+15]) into a cache line. That spatial locality is completely useless until the search interval [lo,hi)[lo, hi)[lo,hi) shrinks to width ≤16\le 16≤16 in the final 444 iterations! The first 161616 probes each fetch a 64-byte line only to read a single 4-byte integer and discard the remaining 60 bytes.
  2. Data-Dependent Memory Addresses Block Hardware Prefetching: The CPU cannot know whether the next probe is mid−stepmid - stepmid−step or mid+stepmid + stepmid+step until the load of A[mid]A[mid]A[mid] completes, preventing memory-level parallelism (MLP).
  3. Power-of-Two Cache-Set Aliasing: When N=220N = 2^{20}N=220, the top probes occur at byte offsets N/2,N/4,3N/4,N/8,…N/2, N/4, 3N/4, N/8, \dotsN/2,N/4,3N/4,N/8,…, which are all large multiples of 212=40962^{12} = 4096212=4096 bytes. Because CPU L1/L2 caches index their cache sets using lower address bits (bits 6…116\dots 116…11), all top binary-search probes map to the exact same cache set, evicting each other even when the working set is tiny!

The Eytzinger (BFS / 1-Indexed Heap) Array Layout

Named after 16th-century genealogist Michaël Eytzinger (and identical to the 1-indexed array layout of a binary heap), the Eytzinger layout stores the implicit binary search tree in Breadth-First Search (BFS) level order starting at index k=1k = 1k=1:

  • The root (overall median) is at B[1]B[1]B[1].
  • For any node at index kkk, its left child (quartile <B[k]< B[k]<B[k]) is at B[2k]B[2k]B[2k] and its right child (quartile geB[k]ge B[k]geB[k]) is at B[2k+1]B[2k + 1]B[2k+1].

Why Eytzinger Unlocks 4-Levels-Ahead Software Prefetching

In the Eytzinger array B[1..N]B[1..N]B[1..N], what are the 16 great-great-grandchildren of node kkk (4 levels down the search tree)? Their indices are the contiguous range:

[16k,  16k+15]\left[16k, \; 16k + 15\right][16k,16k+15]

Because sixteen 32-bit integers equal exactly 646464 bytes (one single cache line!), if we align BBB to a 64-byte boundary, all 16 possible targets 4 steps in the future reside in the exact same cache line starting at &B[16 * k]! Thus, at step kkk, we can unconditionally issue __builtin_prefetch(&B[16 * k]) without knowing which way the next 4 branches will go, keeping 4 independent DRAM loads pipelined in flight simultaneously!

flowchart LR A["Start at Root k = 1"] --> B["Prefetch 4 Levels Ahead: __builtin_prefetch(&B[16 * k])"] B --> C["Branchless Child Step: k = 2 * k + (B[k] < x) Repeat while k <= N"] C --> D["Decode Answer Index: uint32_t shift = __builtin_ffs(~k) ans_node = k >> shift"]
Hardware Reality: Decoding the Final Eytzinger Node with __builtin_ctz(~k)

During the branchless search loop while (k <= N) k = 2 * k + (B[k] < x);, every time B[k] < x is false (meaning B[k]≥xB[k] \ge xB[k]≥x, so B[k]B[k]B[k] is a valid lower_bound candidate!), we take the left branch (2k2k2k), appending a 000-bit to the binary representation of kkk. Every time B[k] < x is true, we take the right branch (2k+12k + 12k+1), appending a 111-bit to kkk. Therefore, the last ancestor where we branched left (B[ancestor]≥xB[\text{ancestor}] \ge xB[ancestor]≥x) is obtained simply by stripping all trailing 111-bits from kkk and shifting right by one more bit: k >> (__builtin_ctz(~k) + 1)! One hardware tzcnt instruction recovers the exact lower_bound node without maintaining a separate best variable inside the loop.

Production C++20 Implementation: 64-Byte Aligned Eytzinger Table with Prefetching

C++2049 lines
#include <bit>
#include <concepts>
#include <cstddef>
#include <cstdint>
#include <span>
#include <vector>

template <std::totally_ordered T>
class EytzingerTable {
public:
    explicit EytzingerTable(std::span<const T> sorted_input)
        : n_(sorted_input.size()), tree_(n_ + 1) {
        std::size_t src_idx = 0;
        build_inorder(1, sorted_input, src_idx);
    }

    // Returns the Eytzinger index k in [1..n_] of the first element >= x,
    // or 0 if all elements are < x.
    std::size_t lower_bound_eytzinger_index(const T& x) const noexcept {
        std::size_t k = 1;
        constexpr std::size_t kPrefetchMultiplier = 16; // 4 levels ahead = 16 elements (64B for uint32_t)

        while (k <= n_) {
            if (k * kPrefetchMultiplier <= n_) {
                __builtin_prefetch(&tree_[k * kPrefetchMultiplier], 0, 1);
            }
            // Branchless step: left child (2k) if tree_[k] >= x, right child (2k+1) if tree_[k] < x
            k = (k << 1) + static_cast<std::size_t>(tree_[k] < x);
        }

        // Strip trailing 1-bits (right branches) + the 0-bit of the last left branch
        const int trailing_ones = std::countr_one(k);
        return k >> (trailing_ones + 1);
    }

    const T& node_value(std::size_t k) const noexcept { return tree_[k]; }

private:
    std::size_t n_;
    std::vector<T> tree_; // 1-indexed: tree_[1 .. n_]

    // Populates tree_ in BFS order via an in-order traversal of the implicit binary tree
    void build_inorder(std::size_t k, std::span<const T> sorted_in, std::size_t& src_idx) noexcept {
        if (k > n_) return;
        build_inorder(k << 1, sorted_in, src_idx);
        tree_[k] = sorted_in[src_idx++];
        build_inorder((k << 1) | 1, sorted_in, src_idx);
    }
};
When NOT to Use the Eytzinger Layout

The Eytzinger layout sacrifices in-order sequential iteration and O(1)O(1)O(1) rank arithmetic (computing how many elements lie between two pointers takes bit manipulation instead of pointer subtraction). Do not use Eytzinger if your workload frequently iterates over sorted ranges [A,B][A, B][A,B]; for range-scan-heavy workloads, use a B-Tree (or B+B^+B+-Tree with 16-key SIMD nodes) which preserves leaf-level sequential order while still packing 4 binary levels per cache line.

Concept Check Indexing Rules of the 1-Indexed Eytzinger (BFS) Array Layout recall

A static sorted set of N keys is rearranged into a 1-indexed Eytzinger array B[1..N] (Breadth-First Search level-order of the implicit binary search tree).

Just like a 1-indexed binary heap, Eytzinger layout places the root at index 1, the two quartiles at indices 2 and 3, the four octiles at indices 4..7, and in general maps node k's left and right children to 2k and 2k + 1.
Concept Check Why Eytzinger Layout Enables 4-Levels-Ahead Software Prefetching apply

In an Eytzinger array of 32-bit integers (`uint32_t`, 4 bytes each), a search loop at index `k` executes `__builtin_prefetch(&B[16 * k])` before advancing `k = 2 * k + (B[k] < x)`.

In a sorted array, the 16 possible probe locations 4 steps ahead are scattered across 16 distant memory regions. In Eytzinger layout, descending 4 levels multiplies k by 2^4 = 16 and adds a 4-bit offset in [0..15], so all 16 candidates sit contiguously in `B[16*k .. 16*k + 15]` (one 64-byte cache line)!
Concept Check Decoding the Final Eytzinger Index via Trailing One-Bit Count apply

After the branchless Eytzinger loop `while (k <= N) k = 2 * k + (B[k] < x);` terminates at an out-of-bounds leaf index `k > N`, we recover the `lower_bound` node using `k >> (std::countr_one(k) + 1)`.

Every step down the tree shifts `k` left by 1 bit and sets the LSB to `0` (left turn, `B[node] >= x`) or `1` (right turn, `B[node] < x`). The tightest `lower_bound` is the deepest ancestor where we turned left (`0`-bit). Counting trailing `1`s via `std::countr_one(k)` (or `__builtin_ffs(~k)`) and right-shifting by `c + 1` strips all subsequent right turns and the left-turn bit itself, landing directly on that ancestor!
Concept Check Associative Cache-Set Aliasing on Power-of-Two Sorted Arrays staff

Khuong & Morin (2017) observed a dramatic performance cliff when running standard `std::lower_bound` on sorted arrays whose size N is a power of two (e.g., N = 2^{20} ints = 4 MB) compared to N = 2^{20} - 123, whereas Eytzinger layout shows no such cliff.

In an 8-way set-associative cache with 4 KB per way, addresses that differ by multiples of 4096 bytes collide in the exact same cache set. For N = 2^{20} ints (4 MB), the top 10 levels of standard binary search all probe addresses that are multiples of 4096 bytes, thrashing a single cache set while leaving the other 63 cache sets cold! Eytzinger packs the top 10 levels contiguously into the first 1024 ints (4 KB), spreading evenly across all cache sets.

Key Takeaways

Standard sorted binary search wastes 60 of every 64 bytes in a cache line during the first log_2(N) - 4 probes and suffers associative cache-set aliasing when N is a power of 2.
The Eytzinger layout stores the implicit binary search tree in 1-indexed BFS order (root at 1, children at 2k and 2k+1), packing the top 4 levels into a single 64-byte cache line.
Because all 16 great-great-grandchildren of node k lie contiguously at indices [16k .. 16k+15], __builtin_prefetch(&tree_[16*k]) prefetches the exact cache line needed 4 steps later.
After the branchless loop while (k <= N) k = 2*k + (tree_[k] < x), the lower_bound node is decoded in O(1) via k >> (std::countr_one(k) + 1).
