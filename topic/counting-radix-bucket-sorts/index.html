Intuition first

Comparison sorts extract only $1$ bit of ordering per operation. Counting Sort and Radix Sort use the key's bits directly as a $b$-way array index—extracting $\log_2 b$ bits of information per array lookup—reducing the tree height from $\Omega(n \log_2 n)$ to $\Theta\!\left(\frac{w}{\log_2 b}(n + b)\right)$.

Counting Sort & Prefix-Sum Stability

When keys are integers in a small range $[0, k)$, Counting Sort bypasses key-to-key comparisons entirely in three linear passes:

  1. Histogram Pass ($\Theta(n)$): Count occurrences of each key in count[0 .. k-1].
  2. Prefix-Sum Pass ($\Theta(k)$): Compute exclusive or inclusive prefix sums so count[v] holds the exact starting (or ending) output index for records with key $v$.
  3. Stable Scatter Pass ($\Theta(n)$): Iterate through the input array and place each element into out[count[key]++] (using exclusive prefix sums in a forward scan, or inclusive prefix sums in a backward scan).
LSD Radix Sort Correctness Invariant: Why the Digit Pass MUST Be Stable

Least-Significant-Digit (LSD) Radix Sort views each $w$-bit key as a $d$-digit base-$b$ number ($d = \lceil w / r \rceil$ where $b = 2^r$) and runs Counting Sort from the least significant digit ($j = 0$) to the most significant digit ($j = d - 1$).

Loop Invariant (Induction on Digit $j$): After pass $j$, the array is sorted by the suffix of the lowest $j + 1$ digits. On pass $j$, two elements $x$ and $y$ either:

  • Have different $j$-th digits ($x_j < y_j$): Counting Sort places $x$ before $y$, correctly ordering them regardless of lower digits.
  • Have equal $j$-th digits ($x_j = y_j$): Their true order is determined by their lower $j$ digits—which were already in sorted order from pass $j - 1$! Stability of Counting Sort guarantees that $x$ and $y$ preserve their relative order from pass $j - 1$. Without stability, pass $j$ scrambles lower-digit ties and produces an unsorted output!

Choosing the Optimal Radix $b = 2^r$ & Sorting Signed/Floating-Point Keys

Given $n$ keys of $w$ bits, if we extract $r$ bits per pass ($b = 2^r$ buckets), we perform $d = w/r$ passes of cost $\Theta(n + 2^r)$. Theoretically, choosing $r = \lfloor \log_2 n \rfloor$ ($b = \Theta(n)$) minimizes $\frac{w}{r}(n + 2^r)$ to $\Theta\!\left(\frac{w}{\log_2 n} \cdot n\right)$. In hardware practice, however, $r = 8$ ($b = 256$ buckets, 4 passes for 32-bit ints, 8 passes for 64-bit ints) is almost universally used because a $256 \times 4\text{ B} = 1\text{ KB}$ histogram array stays permanently pinned in L1d cache and avoids TLB thrashing!

Can Radix Sort handle negative two's-complement integers and IEEE-754 float/double values? Yes—via bijective order-preserving bit flips in $O(1)$ instructions:

  • Signed Two's-Complement int32_t / int64_t: Flipping the sign bit (uint64_t(x) ^ (1ULL << 63)) maps $-2^{63} \mapsto 0$, $-1 \mapsto 2^{63}-1$, $0 \mapsto 2^{63}$, and $2^{63}-1 \mapsto 2^{64}-1$, turning signed order into unsigned lexicographical order!
  • IEEE-754 double (Sign-Magnitude Exponent + Mantissa): Positive floats already sort identically to unsigned integers ($+0.0 < +1.0 < +\infty$). Negative floats have MSB = $1$ and increase in magnitude as they become more negative (reversed order). Michael Herf's FloatFlip bijection flips all 64 bits if the sign bit is $1$, and flips only the sign bit if the sign bit is $0$: uint64_t mask = -int64_t(u >> 63) | (1ULL << 63); return u ^ mask;.

Hardware Reality: TLB Misses & Cache-Line Write-Combining Limits on $b = 2^r$

Why does choosing $r = 16$ ($b = 65{,}536$ buckets, only 2 passes for 32-bit ints) perform worse than $r = 8$ ($b = 256$ buckets, 4 passes) on modern CPUs? During the scatter phase dst[offset[digit]++] = x, the CPU writes simultaneously to $b$ distinct active output streams in memory:

  • Each stream writes to a different $4\text{ KB}$ virtual memory page and $64\text{ B}$ cache line.
  • An x86-64 core has only ~64–128 L1 dTLB entries and 10–12 L1 Line Fill Buffers (write-combining buffers), and an L1d cache holds only 512 cache lines ($32\text{ KB}$).
  • With $b = 256$ buckets, all 256 active write pointers fit inside L1d cache and L2 TLB. With $b = 65{,}536$ buckets, every single write suffers both an L1/L2 cache miss and a page-table walk (TLB miss), collapsing memory throughput by $5\text{–}10\times$!

Production C++20 Implementation: 8-Bit LSD Radix Sort with Signed/Float Bijection & Pass-Skipping

C++20
#include <algorithm>
#include <array>
#include <bit>
#include <cstddef>
#include <cstdint>
#include <vector>

// Bijective order-preserving projections to uint64_t
constexpr std::uint64_t radix_encode_int64(std::int64_t x) noexcept {
    return static_cast<std::uint64_t>(x) ^ (1ULL << 63);
}
constexpr std::int64_t radix_decode_int64(std::uint64_t u) noexcept {
    return static_cast<std::int64_t>(u ^ (1ULL << 63));
}

constexpr std::uint64_t radix_encode_double(double d) noexcept {
    std::uint64_t u = std::bit_cast<std::uint64_t>(d);
    std::uint64_t mask = -static_cast<std::int64_t>(u >> 63) | (1ULL << 63);
    return u ^ mask;
}
constexpr double radix_decode_double(std::uint64_t u) noexcept {
    std::uint64_t mask = ((u >> 63) - 1ULL) | (1ULL << 63);
    return std::bit_cast<double>(u ^ mask);
}

// High-throughput 64-bit LSD Radix Sort (r = 8 bits, 1 histogram pass + skipped trivial passes)
void radix_sort_u64(std::vector<std::uint64_t>& a) {
    const std::size_t n = a.size();
    if (n <= 1) return;

    // 1. Compute all 8 byte histograms in a single sequential scan (8 KB fits in L1d)
    std::array<std::array<std::size_t, 256>, 8> count{};
    for (std::uint64_t v : a) {
        for (std::size_t p = 0; p < 8; ++p) {
            ++count[p][(v >> (p * 8)) & 0xFFU];
        }
    }

    std::vector<std::uint64_t> aux(n);
    std::uint64_t* src = a.data();
    std::uint64_t* dst = aux.data();

    for (std::size_t p = 0; p < 8; ++p) {
        // 2. Convert histogram to exclusive prefix sums & detect trivial single-bucket pass
        bool trivial = false;
        std::size_t sum = 0;
        for (std::size_t b = 0; b < 256; ++b) {
            if (count[p][b] == n) { trivial = true; break; }
            std::size_t c = count[p][b];
            count[p][b] = sum;
            sum += c;
        }
        if (trivial) continue; // All elements have identical byte p!

        // 3. Stable scatter pass
        const std::size_t shift = p * 8;
        for (std::size_t i = 0; i < n; ++i) {
            const std::uint64_t v = src[i];
            const std::size_t bucket = (v >> shift) & 0xFFU;
            dst[count[p][bucket]++] = v;
        }
        std::swap(src, dst);
    }

    if (src != a.data()) {
        std::copy(src, src + n, a.data());
    }
}
Floating-Point NaN & Signed Zero (-0.0 vs +0.0) in Radix Sort

When applying radix_encode_double to IEEE-754 floats, be aware of two edge cases: (1) -0.0 (0x8000000000000000) and +0.0 (0x0000000000000000) map to adjacent unsigned integers (0x7FFFFFFFFFFFFFFF and 0x8000000000000000), which cleanly sorts -0.0 immediately before +0.0 (total order), and (2) NaN payloads have all exponent bits set to 1 and sort to the extreme ends. Normalizing if (d == 0.0) d = +0.0; before encoding ensures canonical zero equality if needed.

Concept Check Why LSD Radix Sort Requires a Stable Digit Sort recall

An engineer implements Least-Significant-Digit (LSD) Radix Sort on 2-digit base-10 numbers `[42, 15, 41, 12]`, but replaces the stable Counting Sort pass with an unstable in-place bucket partition.

LSD Radix Sort's inductive invariant relies on Pass j preserving the relative order of all elements that tie on digit j, because their relative order on digits 0..j-1 was already established by the preceding passes. If Pass j is unstable, elements with equal most-significant digits end up arbitrarily ordered on their lower digits.
Concept Check Sorting Signed 64-Bit Two's-Complement Integers with Unsigned Radix Sort apply

You have a fast unsigned 64-bit LSD Radix Sort `radix_sort_u64` and need to sort an array of signed `int64_t` values (which include negative numbers like `-1` = `0xFFFFFFFFFFFFFFFF` and `INT64_MIN` = `0x8000000000000000`).

In two's-complement representation, negative numbers have MSB = 1 and increase monotonically from INT64_MIN (0x8000...0) to -1 (0xFFFF...F), while non-negative numbers have MSB = 0 and increase from 0 (0x0000...0) to INT64_MAX (0x7FFF...F). Flipping only the MSB (bit 63) shifts non-negative numbers to the upper half [2^63, 2^64-1] and negative numbers to the lower half [0, 2^63-1] while preserving monotonicity within both halves!
Concept Check Choosing Radix Width r = 8 vs r = 16 on Modern CPU Caches and TLBs apply

To sort $n = 10{,}000{,}000$ 32-bit integers, an engineer considers $r = 8$ bits ($256$ buckets, $4$ passes) vs. $r = 16$ bits ($65{,}536$ buckets, $2$ passes).

In the scatter loop `dst[offset[bucket]++] = x`, each active bucket pointer addresses a different cache line and (for large n) a different 4 KB virtual page. When the number of active buckets b = 65,536 exceeds the L1/L2 TLB capacity (typically 64–1,536 pages) and L1 cache lines (512 lines), almost every scatter write triggers a page-table walk and cache miss. Keeping r = 8 (256 buckets) or r = 11 (2,048 buckets) avoids TLB thrashing.
Concept Check Sorting IEEE-754 Floating-Point Numbers via Herf's FloatFlip Bijection staff

IEEE-754 `double` values use sign-magnitude encoding: bit 63 is the sign bit, bits 52..62 are the biased exponent, and bits 0..51 are the mantissa. Positive doubles already sort in exact unsigned integer order (`std::bit_cast<uint64_t>`), but negative doubles have MSB = 1 and grow in unsigned bit value as they become *more negative* (e.g., `-2.0` has a larger bit pattern than `-1.0`).

Because IEEE-754 is sign-magnitude rather than two's-complement, flipping only bit 63 would place negative numbers in the lower half `[0, 2^63)` in *reverse* order (`-0.0 < -1.0 < -2.0 < -∞`). By flipping ALL 64 bits (`~u`) when bit 63 is 1, negative numbers map to `[0, 2^63)` in proper ascending order (`-∞` near 0 up to `-0.0` at `2^63 - 1`), while flipping only bit 63 when bit 63 is 0 maps positive numbers to `[2^63, 2^64)`.

Key Takeaways

Counting Sort uses cumulative prefix sums to stably place n integers from [0, k) in Θ(n + k) time without key-to-key comparisons.
LSD Radix Sort requires its inner digit sort to be strictly stable so ties on more significant digits preserve the ordering established by less significant digits.
Using 8-bit digits (256 buckets) keeps the histogram in L1 cache and avoids TLB thrashing across active write streams; computing all byte histograms in one initial scan allows skipping passes where all keys share the same byte.
Signed two's-complement integers and IEEE-754 floats can be sorted in linear time via O(1) bijective bit flips (flipping MSB for signed ints; FloatFlip mask for IEEE-754 floats).
